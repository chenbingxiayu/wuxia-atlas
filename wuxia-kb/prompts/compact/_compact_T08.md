# SKILL 03h: 地名地段分类规则

> 为《史记》2116 个 place 实体打上"地段"二级分类（水域/山脉/郡/县/城邑…）。原则：**规则沉淀 > 一次拍脑袋**——每发现一批误分类，提炼出规则记录在本文档，改进脚本重跑即可。

**一、分类体系（14 类 + 未分类）**：水域（黄河/渭水/昆明池）、山脉（泰山）、原野（牧野）、关隘（函谷关）、区域（关中/江南）、国家（大夏/大宛/夜郎）、州、郡、县（汉代侯国=县级行政区）、城邑（咸阳/邯郸）、建筑（阿房宫）、陵墓（霸陵）、乡里（中阳里）、道桥（孟津）；另有 误标（五帝/乾封等非地名修辞典故）、待拆分（新丰鸿门/泰山梁父等复合地名）、（空）。允许一个地名多个标签（多标签 250→343 个）。

**二、六级流水线（决策顺序，全部已实现）**：

# SKILL 06e: 概念分类树构建 — Bottom-Up 归纳与颗粒度调整

> **核心理念**：分类不是先验的，是从数据中归纳的。  
> 先有实例，再有类；先看数量，再定颗粒度。

---

## 一、何时使用

| 场景 | 信号 |
|------|------|
| 新一批实体已标注，需要建立分类体系 | 索引中有大量无分类实体 |
| 某叶子类实例数 > 50，内部有明显子结构 | 拆分信号：子结构可通过朝代/职能/地域切分 |
| 某叶子类实例数 < 10，且与邻类高度相关 | 合并信号：单独列类没有辨别力 |
| 分类树 MD 与 TTL 不一致 | 有人手工编辑了 MD，需要以 TTL 为准重生 |
| 需要补全缺失的实体（如某朝代帝王未入树） | 缺口分析发现高频实体未入树 |

**不适用**：从零设计一个全新实体类型的本体（用 SKILL_06a）。

---

## 二、Bottom-Up 构建流程（5步）

### Step 1. 实例统计与分桶

从 `entity_index.json` 提取目标实体类型，按出现频次分桶：

```bash
python kg/taxonomy/scripts/person_gap_report.py
```

| 频次桶 | 处理策略 |
|--------|---------|
| ≥ 50 | 必须入树；出现次数高说明文本中确实重要 |
| 20–49 | 必须入树 |
| 10–19 | 应入树 |
| 5–9 | 建议入树，上下文验证后加入 |
| 2–4 | 择优：确认非别名后加入 |
| 1 | 留待批量脚本处理；人工成本过高 |

**关键动作**：区分"真实新实例"与"别名"——后者不需要新分类条目，只需在 `entity_aliases.json` 建立映射。

### Step 2. 归纳初始分类

对 Step 1 筛出的高频实体，自底向上归纳分组。归纳信号按优先级：

1. **显式归属**：白名单（rulers.json / shihao_index.json）直接确定类别
2. **章节信号**：主要出现在专题列传（刺客/酷吏/货殖等）→ 直接对应类
3. **名称后缀**：单于/夫人/公子/太子 → 对应特定类
4. **共现模式**：与已知类成员高度共现 → 同类推断
5. **历史常识**：帝王世系表（如夏本纪17王、商本纪序列）→ 补全空白

**多信号原则**：至少两个独立信号才可信。单信号分类历史准确率约 12%（见 SKILL_06a §5 记录）。

### Step 3. 颗粒度调整

这是 06e 的核心步骤。**颗粒度信号**：

#### 拆分信号（leaf class 实例数 > 50）

当某叶子类超过 50 个实例，检查内部是否有可切分维度：

```
信号A：时间维度 — 早/中/晚期（如秦国历代君主：秦孝公前/商鞅变法后/统一后）
信号B：职能维度 — 文臣/武将/外交（如汉臣可拆）
信号C：地域维度 — 关中/山东/荆楚（如战国策士分布）
信号D：历史阶段 — 如"汉初"/"汉中后"已拆分
```

拆分阈值建议：
- 子类实例数 ≥ 10 → 值得单独列类
- 子类实例数 < 10 → 合入父类或"其他"桶

#### 合并信号（leaf class 实例数 < 10）

当叶子类过小，考虑：
- 合并到邻近类（功能相似、时代相近）
- 提升为父类的实例（不单独设子类）
- 保留但标注"稀疏类"（<10，可能扩充）

#### 实操判断表

| 现状 | 建议操作 | TTL 修改 |
|------|---------|---------|
| 某类 > 100 且内部异质性高 | 必须拆分 | 新建子类，移动实例 |
| 某类 50–100 且有清晰切分维度 | 建议拆分 | 同上 |
| 某类 10–50 | 保持，继续观察 | 只新增实例 |
| 某类 < 10，与邻类功能重叠 | 合并 | 改 rdf:type，删子类 |
| 某类 < 5，历史上确实独特 | 保留为稀疏类 | 加注释说明 |

### Step 4. TTL 追加与校验

**追加格式**：

```turtle
per:少康 a per:夏 ; rdfs:label "少康"@zh ; :count 8 .
per:帝槐 a per:夏 ; rdfs:label "帝槐"@zh ; :count 3 .
```

**校验三步**：

```python
# 4.1 语法
from rdflib import Graph
g = Graph(); g.parse('kg/taxonomy/person.ttl', format='turtle')
print(f'{len(g)} triples')  # 不报错即通过

# 4.2 冗余检查（重跑 gap report）
python kg/taxonomy/scripts/person_gap_report.py
# TTL 冗余 < 100 为合格

# 4.3 没有实例游离在父类（本级）中未入子类
```

### Step 5. 重生分类树 MD

```bash
python kg/taxonomy/scripts/build_taxonomy.py kg/taxonomy/person.ttl
# → kg/taxonomy/person_taxonomy.md
```

对应 HTML（如有）同步重跑：
```bash
python kg/taxonomy/scripts/rebuild_person_tree_html.py
```

## 三、颗粒度设计原则

### 垂直粒度（层次深度）

| 层级 | 示例（人物树） | 原则 |
|------|-------------|------|
| L0 | 人物 | 顶层锚点，不挂实例 |
| L1 | 王室 / 臣 / 诸子百家 | 大类，<100 类覆盖全域 |
| L2 | 帝王 / 诸侯 / 后妃 / 宗室 | 中类，每类 20–200 实例 |
| L3 | 夏 / 商 / 周 / 汉 | 叶类，每类 10–80 实例 |
| L4 | （仅当 L3 > 80 才拆） | 如"汉初"/"汉中后" |

**原则**：树深不超过 4 层；实例只挂在叶节点。

### 水平粒度（同层类数）

- 同一父类下子类数量建议 3–12 个
- < 3 个说明粒度太粗（考虑下移）
- > 15 个说明粒度太细（考虑合并或引入中间层）

### 正确案例（汉代帝王拆分）

```
汉（帝王）→ 汉（5人，高祖/惠帝/文帝/景帝/武帝等）
```
汉代帝王本可单独列出每一任，但 史记 时段只到武帝，所以合并为一类（约 10 人）是合适颗粒度。

### 反例（过细导致空类）

```
# 错误：为 1-2 人建类，无扩充空间
per:帝皋 a owl:Class ; rdfs:subClassOf per:夏 .  # ❌ 太细
```

正确做法：1-3 人的小类直接挂在父类下作为实例，不单独建子类。

## 四、缺口补全工作流

当发现某朝代/某类别大量缺失（如夏朝帝王）：

1. **查历史序列**：从史书（如夏本纪）获取完整列表
2. **比对索引**：`entity_index.json` 中查找各名称的出现频次
3. **频次筛选**：≥ 3 次出现的必须入树
4. **别名去重**：同一人的多种称谓只建一个 TTL 实例
5. **TTL 追加**：按频次排序插入
6. **重生 MD**：运行 `build_taxonomy.py`

# SKILL 06a: 实体到本体管线 — 从标注文本到 RDF 分类本体

> 核心原则：**本体不是凭空设计的，而是从标注实例中逐层归纳涌现**（Bottom-up）。以生物类（388 种）为首个实例。

**管线**：chapter_md/*.tagged.md →（build_entity_index.py）entity_index.json 实体索引 →（人工/LLM 分类）{type}_wordlist.json 分类词表（多层分类树+歧义标记）→ {type}_taxonomy.md 可读分类树 → kg/taxonomy/{type}.ttl OWL/RDF 本体（类+实例+属性）。

**Step 1 从实体索引提取类型词表（含词条简介）**：按出现次数排序、归纳分类维度；每个词条附一句从上下文自动提取的简介（提取 ±15 字上下文→LLM 总结，或章节标题+共现身份/官职词拼接）。为什么简介重要：韩信（333 次）主现于高祖本纪但实为"将领"、司马相如（104 次）主现于列传但实为"文学家"、赵高（139 次）主现于秦始皇本纪但实为"宦官"——有简介即可基于语义而非章节位置分类。**词表阶段的简介投资，在本体分类阶段获得十倍回报**。词表三层结构：always_{type}（确定类别）/context_dependent（歧义规则，如 "龙：天降龙=生物; 龙颜=比喻"）/new_candidates。

**Step 2 设计分类树（类层次，3-4 层）**。类名命名原则：①**自明性**——✗ `燕 [7人]`（是诸侯/燕国还是臣/春秋/燕？）✓ `燕国臣子 [7人]`（清晰无歧义）；②**无歧义**——同名不能出现在不同父类下（"齐国臣子(春秋)"与"齐国臣子(战国)"）；③**语义完整**——子类名应包含父类语义（不要用"将""相"，用"秦国将领""秦国相臣"）；④**用中文**——避免拼音碰撞（Han=汉≠韩）。设计原则（对应 Ontology 101 Step 4）：自底向上（从实例归纳类，不从理论推演类）；中间层最丰富（顶层过粗、底层过细）；允许集合类（"六畜""五穀""鸟兽"是独立概念，单列集合泛称）；神话类单列（龙/凤麒麟跨生物/神话边界）。

**Step 3 生成可读分类树（Markdown）**：从 entity_index+分类规则自动生成，每种实体列出现次数、按次数降序。

**Step 4 生成 RDF/OWL 本体（Turtle）**：类名 ASCII 英文（bio:Equine）、中文放 rdfs:label；实例 `bio:i_{pinyin}`；属性 `:count`（出现次数）；rdflib 解析验证语法。

**Step 5 反思验证（Reflection）——自动分类必须经过反思验证**。初次分类错误率可能极高：人物帝王类首次分类 437 人中仅 49 人正确（88% 误分率）。方法=逐类审查：列所有实例→逐一检验分类信号（是否在帝王名册中/名称是否匹配帝号模式/是否本纪标题人物）→三信号均不满足判定误分类→分析误分原因→修正规则。v1"主章=本纪→帝王"准确率仅 12% → v2"帝王名册 ∪ 帝号模式 ∪ 本纪标题人物" ~95%。**通用反思原则**：高频实例优先审查；**单信号不可靠**（至少两个独立信号叠加，如 章节+名称）；误分析产出规则（"为什么错"比"哪些错"更重要）；先审大类后审小类；保留"其他"类；区分分组维度与语义断言；历史语境影响分类（秦国=诸侯，秦朝=帝国）；拆分后必须清理(本级)残留；章节信号≠所属国家（跨国叙事：三家分晋、出使匈奴）；逐一审查子类实例。**七种反复出现的错误模式**：章节信号误导（❌ 韩信因出现在本纪→被误分为帝王）/国王混入臣子（白公胜）/汉人混入外邦（张骞）/类名歧义（燕）/平铺非嵌套/(本级)残留/URI 碰撞。

**Step 6 迭代优化**：合并过细的类（叶子仅 1-2 实例）；拆分过粗的类（>50 实例且内部有明显子群）；处理多归属（10.6% 高频人物属两个以上分类，如 项羽=帝王+将相——RDF 用 `a per:Emperor , per:GeneralMinister` 表达多类型）；补充属性（:count 外加 rdfs:comment/rdfs:seeAlso）。

**人物本体的特殊之处（vs 生物）**：类-实例关系 1:N（项羽→帝王+将相）；分类信号来自章节结构——**文献体例即分类学**（本纪=帝王、世家=诸侯重臣、列传标题直接给出人物类型）；三层信号叠加=章节信号（最强）+名称模式+共现信号。成果对照：生物 20 类/294 三元组/1 轮反思 vs 人物 142 类/~5,826 三元组/10+ 轮反思。

**关键方法论（五条）**：①单信号分类灾难性不可靠（帝王类仅凭"主章=本纪"准确率 12%，至少两个独立信号叠加验证）②分类从边缘案例中涌现（实例误分暴露规则缺陷，修正规则→改进分类树）③反思收敛（每轮发现的问题越来越少）④章节信号≠所属国家是最大陷阱 ⑤拆分后必须清理(本级)残留。
