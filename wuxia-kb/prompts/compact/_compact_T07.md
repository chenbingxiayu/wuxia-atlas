# 元技能12: 数据融合 — 多源数据对齐与消歧

> 核心思想："来自不同工序的结果,需要对齐、消歧、去重,形成统一的知识视图"。（本版为方法论忠实缩写：融合层次/四层消歧架构/多数投票与人工覆盖/冲突解决策略不减，算法代码压缩为规则表述。）

### 核心挑战

1. **同一实体,不同表述**:刘邦 = 沛公 = 汉王 = 高祖 = 高帝
2. **同一事件,多章记述**:秦本纪、六国年表、赵世家对长平之战的不同描述
3. **跨工序一致性**:事件索引的年份 ↔ 年表数据 ↔ 人物生卒年
4. **冲突解决**:不同来源的矛盾数据如何处理?

### 融合层次（L1–L5 各层职责表，完整保留）

```
L1: 字符串层面 → 归一化、去重、别名映射
L2: 实体层面 → 消歧、规范化、别名合并
L3: 事件层面 → 跨章合并、多源整合
L4: SKU层面 → 结构化知识单元的拼接
L5: 知识图谱层面 → 全局一致性、关系网络
```

## 二、字符串层面融合（L1）

- **别名检测**：策略1前缀包含检测（长名包含短名+同章共现；唯一映射→自动确认，多映射→人工审查。✅ "庄襄王"⊂"秦庄襄王"且唯一 → 自动确认）；策略2帝号特殊模式（"帝X"→"X"，商朝帝号规律）；策略3姓氏分组（共享姓氏→标记"不确定"需人工审查。❌ 赵本学/赵耿、公孙侨/公孙鞅——不是别名，是不同的人）。
- **双向索引防重**：aliases[canonical]=[alias...] 与 reverse[any_name]=canonical 双向维护；两者已各有不同规范名时跳过不合并。保证：任意名称只映射到唯一规范名（反向索引约束）。
- **字符串归一化**：异体字处理（钜→巨、於→于、寔→实）；标注符号清理（移除〖TYPE ...〗再算相似度/搜索）。
- **名称相似度**：|shared_chars| / min(|a|,|b|)。阈值（基于A/B测试）：≥0.8 高置信度（几乎确定同一事件）；≥0.6 中等置信度（需额外证据，如共享人物/时间）；<0.6 低相关性（可能无关）。

## 三、实体层面融合（L2）

### 3.1 实体消歧：四层启发式策略（逐层保留）

问题："〖@武王〗伐纣"——武王=周武王? 秦武王? 楚武王?

- **层1 前置邦国标记**：向前扫描20字符查找最近的&state&标记；模式 &state&@short_name@ → 如 &周&@武王@ → 周武王。
- **层2 邻近邦国提及**：在±80字符窗口内查找&state&标记，取距离最近的邦国；优先左侧（上文），其次右侧。
- **层3 章节主题邦国**：CHAPTER_STATE 表（004→周、005→秦、043→赵…130章映射）兜底；005章(秦本纪)中的"武王"→秦武王。
- **层4 共现全名查找**：在章节中查找包含短名的全名；唯一候选→自动确认；多候选→标记歧义需人工决策。

### 3.1a 冲突解决：多数投票 + 人工覆盖（完整保留）

- 多数投票：无候选 → 无法消歧；全部一致（count == len(candidates)）→ 采纳，高置信度；≥2/3 多数（count >= len(candidates) * 0.67）→ 采纳，中等置信度；分裂决策 → 人工审查（标记需review）。
- 人工覆盖：MANUAL_CORRECTIONS 优先级最高，如 ('004','元王'):'周元王'（覆盖nearby_state=楚的误判）、('005','王'):'秦王'。

### 3.2 实体索引合并（压缩）

build_entity_index.py：从全部标注文本提取实体 → 消歧短名（disambig_map）→ 别名反向索引归并 → 聚合 aliases/chapters/para_refs/count，输出 entity_index.json。输出结构（person.刘邦）：aliases ["沛公","汉王","高祖","高帝","刘季"]、chapters、para_refs、count。

### 3.3 内联消歧语法

语法 `〖@surface|canonical〗`：013章〖@台|吕台〗、047章〖@台|柳下季〗。渲染：显示 surface，链接/悬停指向规范名。

**典型案例："武王"的上下文消歧**：004周本纪〖&周&〗〖@武王〗伐纣 → 前置邦国标记 → 周武王 ✅；005秦本纪"昭襄王卒,子〖@武王〗立" → 章节主题邦国 → 秦武王 ✅；043赵世家〖@武王〗即位,封其弟〖@平原君〗 → 平原君是赵国人 → 赵武王 ✅。

## 四、事件层面融合（L3）

### 4.1 跨章事件对齐（cross_ref）

多因子匹配判据（需同时满足多个条件）：①名称相似度≥阈值 ②共享人物≥N个 ③年份接近（如有CE标注）。name_sim>=0.8 且共享>=1人物 → conf 0.95；name_sim>=0.6 且共享>=2人物 且年差<=5 → conf 0.85。

### 4.2 战争事件多源合并（六阶段流水线，压缩）

原始提取→自动分组（按清理后的名称分组，736条→308组）→细节提取（交战双方/伤亡数/战果）→冲突检测（年份不一致/伤亡数差异>2倍/战果矛盾）→LLM增强（计划中）→导出。合并策略：名称取最常见；人物/地点合并集合；年份取众数并记录 year_conflicts；描述保留所有来源比对。

### 4.3 年表×事件融合（两轮推理，压缩）

Round1 直接证据匹配（编年表特征事件=high、人物卒年=high、人物活跃年中位数=medium）；Round2 插值推断（双锚点线性插值=low、单锚点外推=very_low）。验证：人物在世约束、章节纪元约束、单锚点塌缩检测（>50%事件同年=锚点污染）。

## 六、冲突解决策略

### 6.1 冲突类型分类

| 类型 | 示例 | 来源 |
|------|------|------|
| **年份冲突** | 事件A在章节X标注为-260,在章节Y标注为-259 | 跨章记述差异 |
| **伤亡数冲突** | 同一战争,来源A说40万,来源B说45万 | 史料记载不一 |
| **身份冲突** | "武王"在不同章节指不同人 | 短名歧义 |
| **关系冲突** | 两个事件,来源A说有因果,来源B说无关 | 推理差异 |
| **时序冲突** | 事件A的year < 事件B的year,但描述说B在A之前 | 标注错误 |

### 6.2 解决策略矩阵

| 冲突类型 | 策略 | 实施 |
|---------|------|------|
| **年份冲突(小)** | 取众数(majority voting) | `Counter(years).most_common(1)[0]` |
| **年份冲突(大)** | 保留所有,标注`year_conflicts` | 记录在JSON,人工review |
| **伤亡数冲突** | 保留所有,标注来源 | `casualties: [{source, number}, ...]` |
| **身份冲突** | 上下文消歧 | 四层启发式策略 |
| **关系冲突** | 置信度加权 | 保留高置信度关系 |
| **时序冲突** | 约束检查 | lint检测,人工修正 |

### 6.3 冲突记录模式

**原则**：不强制解决，记录所有观点。示例（长平之战）：年份 -260 得2票(005-042,043-067)、-259 得1票(015-108) → majority_vote 取 -260 并记录冲突 ✅；伤亡 45万(斩首) vs 40万(坑杀) → keep_all 双保留 ✅。

### 6.4 人工覆盖机制（完整保留）

MANUAL_CORRECTIONS 三类修正：①(章节,短名)→规范名；②事件年份修正（覆盖自动推断，附reason：'跨章交叉验证,本纪与世家一致为-260'）；③别名关系修正（merge/split，如 ('person','庄子','庄周'):'merge' 确认同一人、('person','李斯','李子'):'split' 确认不是同一人）。应用时记录 log_correction(key, 旧值, 新值, '人工修正')。

## 十、总结（压缩）

1. 分层融合：字符串→实体→事件→SKU→知识图谱；2. 多源验证：跨章节、跨数据源交叉验证；3. 冲突记录：不强制解决,保留所有观点；4. 人工覆盖：关键决策保留人工修正机制；5. 质量保障：一致性校验（反向索引一致性/sequel时序/实体引用完整/跨工序年份不冲突）+覆盖率统计+增量监控。

融合质量报告实测：事件年份覆盖率 98.7% (3,051/3,185)；实体消歧覆盖率 92.4% (595/644)；跨章对齐事件 294个；冲突记录数 73个。

**融合理念**：允许不一致（冲突记录在 conflicts 字段）、多元真值（保留所有来源观点）、累积式更新（新旧共存带时间戳）、可追溯性（每条数据标注 _source）。核心洞察：历史研究不是寻找唯一答案,而是理解多种可能性——融合的目的不是消除差异,而是结构化地呈现差异。

# SKILL 03b: 人名消歧 — 从短称到唯一指称

> 从《史记》130篇 4,921 个人名的消歧实践中提炼，适用于古籍中同名异指的自动化解决。（本版为方法论忠实缩写：4 列别名结构、消歧策略清单、同名异人处理不减。）

## 一、4 列别名结构（完整保留）

`entity_aliases.json` 为按实体类型分片的 4 列表结构（surface / type / canonical / refs）：

```json
{
  "person": [
    {"surface": "昭王", "type": "person", "canonical": "秦昭王",
     "refs": [["005_秦本纪","20.1"], ["071_樗里子甘茂列传","3"]]},
    {"surface": "昭王", "type": "person", "canonical": "燕昭王",
     "refs": [["034_燕召公世家","17"]]}
  ]
}
```

**关键属性**：
- **同 surface 多 canonical 允许并存**：歧义 surface 按 canonical 拆多行（"昭王" 3 行分别指 秦/燕/楚昭王）；
- **refs 记录证据**：每条 (surface, canonical) 绑定到具体章节/段落，便于回查；
- **类型分片**：跨类型不混（人名"汉"和邦国"汉"完全独立）。

规模（2026-04-19）：人名实体 4,921；别名条目 3,322（旧版 591→3,322）；唯一 canonical 2,097；歧义短名 550；章节级映射 644（覆盖 71 章）。

渲染层解析顺序：内联消歧〖@X|Y〗 → disambiguation_map[章节][短名] → entity_aliases 按 refs 匹配当前章节 → 兜底保留 surface 为 canonical。

数据来源优先级（抽取合并时前者优先）：①tagged.md 的〖@X|Y〗内联消歧（最权威，作者实际标注）②disambiguation_map.json（章节级短名→全名）③rulers.json 别名字段（656条君主数据）④先秦称呼对照表 ⑤旧 entity_aliases.json（legacy 保底）。

## 二、消歧策略清单（完整保留）

两种消歧方式可混用：**方式A** 外部JSON消歧（章节级，不改源文件）；**方式B** 内联消歧 `〖TYPE X|Y〗`（标注即消歧，内联 | 后的规范名优先级高于JSON）。

**四层启发式（按优先级）**：
1. 前缀国名（最精确，前10字符内有&国名&）：&秦&@昭王@ → 秦昭王（置信度：极高）；
2. 附近国名（80字窗口内的&国名&或@国名X@）：置信度高；
3. 章节主题国（CHAPTER_STATE表兜底）：周本纪(004)中的"武王"→默认周武王（置信度：中高）；
4. 共现全名（同章出现@秦昭王@和@昭王@ → "昭王"指秦昭王；置信度：中）。

**多数投票与冲突处理**：同一(章节,短名)的多次消歧结果，≥2/3 一致 → 采用；票数分裂 → 跳过不消歧（保守原则：错误消歧比缺失更有害）。

**三层歧义结构**：①谥号歧义（最常见，81个——"武王"→周/秦/楚武王）；②同国同谥号歧义（罕见）；③通称歧义（太子/王/公子——需段落级处理，当前不消歧）。

**不需消歧（SKIP_NAMES）**：帝号（孝文帝）、上古人物（黄帝）、已含国名全称（齐桓公）、汉代封号（梁孝王）、通称性短名（太后/太公/周公）、带前缀复合谥号（惠文王）。

**已知错误模式**：附近国名误导（周本纪"&燕&…@惠王@"误判燕惠王，实际周惠王→MANUAL_CORRECTIONS 覆盖）；多国并提段落；主题国与短名不匹配（策略2与策略3冲突时优先策略2）；单字人名假阳性（"象"天、"日益"）；同章多指代 6 条无法章节级消歧。

## 三、同名异人处理与 canonical 规范（完整保留）

**命名规则**：先秦诸侯=国+谥号（周武王/秦昭王）；秦始皇=秦始皇帝；汉帝=汉+通称（汉高祖）；诸侯王=封国+谥号（楚元王）；其他人物=最常用名（项羽/商鞅）。原则：唯一性/源文忠实/个人名降为alias/旧canonical自动合并。

**🚨 铁律：禁止"谥号+本名"合并作 canonical**——消歧本名时 canonical 只能二选一：纯谥号/封号，或姓+名：

| ❌ 错（谥号+名） | ✅ 对（姓+名） |
|----------------|--------------|
| `〖@贷\|齐康公贷〗` | `〖@贷\|吕贷〗` |
| `〖@政\|秦王政〗` | `〖@政\|嬴政〗` |

**例外（明文特例，不得机械替换）**：
1. 同名异人不可区分→保留"爵号/封号+名"：`〖@信|韩王信〗`（姓+名=`韩信`，与淮阴侯韩信撞名，全库约37处）；
2. 妃子/女性亲属→保留"夫君谥号+妃名"（`〖@郑袖|楚怀王郑袖〗`——surface 已是"国名+姓/女性号"复合形式，无独立家族姓氏系谱）；
3. 身份复合名（太子/公子/王子等身份词不是谥号）→保留原形（`〖@丹|太子丹〗`）。

**canonical 与上下文邦国必须一致**：❌ 陈国语境写〖@灵公|楚灵公〗 → ✅〖@灵公|陈灵公〗。

**处理流程（同名异人/异名同人两分）**：@武王@→章节级消歧→周武王→别名解析→canonical（同名异人路径）；@沛公@→别名解析→汉高祖（异名同人，不需消歧）。章节级假设一章一短名一指代，同章多指代时保守跳过。

# SKILL 02h: 词表构建（通用原则）

> 词表（glossary）= 面向某一领域的**受控词汇表**，为知识图谱、索引、消歧提供基础数据。
> 本 Skill 只讲**通用原则与流程框架**，不展开任何具体领域。领域指引见 §七 交叉索引。

## 一、任务定义

词表构建是从史记全文中系统提取与组织特定类型词汇：

1. **成语典故** — 固化语言单元（语言层）
2. **专有名词** — 人名/官职/地名/族群（指称层）
3. **术语体系** — 礼制、历法、度量衡（概念层）
4. **文化词汇** — 器物、服饰、音乐、祭祀（领域层）

**与邻近 Skill 的分工**：
- **02e 词法分析**：字词级统计、词性标注（面向语言学）
- **02h 词表构建**：领域词汇提取、受控词表组织（面向知识图谱） ← 本篇
- **03a 实体标注**：在原文中用 `〖〗` 标注实体
- **03b 实体消歧** / **03j 人名分类**：surface → canonical 的消歧与分类体系

## 二、词条的通用字段

无论领域，词条基本字段一致：

```json

  "canonical": "规范形式",
  "type": "领域类型（成语/官职/地名/...）",

```

**四列结构**：`surface / type / canonical / refs` 已成为本项目词表的通用骨架。首次在人名别名（2026-04-19）中启用，现推广为统一字段。

## 三、通用工作流程

### 3.1 词条收集

三种来源：

1. **基于已标注实体**：扫描 `chapter_md/*.tagged.md` 提取特定类型标记（例如所有 `〖;〗` 官职）
2. **基于候选词表**：从 02e 的统计候选中筛选
3. **基于外部知识**：对照《汉书》《说文解字》《索隐》《正义》等典籍

### 3.2 定位与匹配

**核心约束**：词条必须锚定到《史记》原文段落，否则归为"叙事性总结"需单独处理。

**技术要点**：
- 去标注纯文本 + 位置映射（`build_strip_map` 模式，见 `scripts/reflect_chengyu_round2c.py`）
- 异体字归并（常见：`脣→唇`、`甕→瓮`、`於→于`、`穀→谷`、`説→说`、`飜→翻`）
- 全半角标点规范化

### 3.3 释义与标注

**释义来源**：
1. 现代工具书（《汉语大词典》《辞海》）
2. 史记三家注（集解/索隐/正义）
3. AI 生成初稿 + 人工校对

**标注同步**：如果词条对应一个原文可标注的片段，**必须在 tagged.md 中加标注**（`〖〗`/`〘〙`/`⟦⟧`）后回填词表。未能标注的叙事性条目单独存于 `*_summarized.json`。

### 3.4 发布与集成

**输出格式**：
- JSON（供程序）
- Markdown（供人）
- HTML（专项索引页，集成到 `docs/special/special_index.html`）

## 四、质量控制

### 4.1 定位率

- 目标：≥95% 的词条定位到原文段落
- 手段：精确匹配 → 规范化匹配 → 分句匹配三级兜底
- 例外：括号叙事性总结（后人概括）作为 `narrative` 单独保留

### 4.2 验证分类

对每条词表条目运行"原文可证性"分类（参考成语识别 02k §6）：

| 状态 | 含义 |
|------|------|
| tagged | 章节中已有直接标注 |
| verbatim | 原文栏直接出现在纯文本中 |
| partial | 分句/省略号拆分后部分出现 |
| narrative | 原文栏是括号叙事 |
| unverified | 在纯文本中完全找不到 → **必须处理**（修正或删除）|

### 4.3 数据一致性

- 章节编号：三位数（001–130）
- 段落编号：`[N]` 或 `[N.M]`（Purple Numbers）
- 规范名：与 `kg/entities/` 的 canonical 字段同步

## 五、双轨数据架构（通用模式）

对任意领域的词表，推荐分两个文件独立生成，互不冲掉：

- **`<topic>.json`**：已标注条目，由扫描 tagged.md 的脚本生成
- **`<topic>_summarized.json`**：未标注但相关的条目，由扫描源词表的脚本生成

源词表（`kg/vocabularies/data/`）保持**人工维护**，两个 JSON 都是派生视图；源词表修改后重跑脚本即可。
