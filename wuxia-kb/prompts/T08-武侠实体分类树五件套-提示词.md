## 四、L2：章节上下文规则

### 4.1 汉代侯者年表 → 县（**已实现** @ 2026-04-18）

**规则**：若 `place.refs` 中出现在以下章节的频次 ≥ 所有引用的 50%，且 L4 后缀规则给出的类别是空或"城邑"（弱类别），则改判为 **县**（汉代侯国 = 县级行政区）。

涉及章节（前 3 位数字匹配）：

- `018_高祖功臣侯者年表`
- `019_惠景间侯者年表`
- `020_建元以来侯者年表`
- `021_建元已来王子侯者年表`

**保护类别**（不被改写）：郡、州、山脉、水域、建筑、陵墓、关隘、区域、海野、乡里、道桥、以及 L1 白名单中已显式分派者。

**关键参数**（`classify_places.py`）：
- `HOUZHE_MAJORITY = 0.5`
- `HOUZHE_MIN_REFS = 1`（单条 ref 命中即可，因大量冷僻侯国只在年表出现一次）

**已知误判**：

## 五·一、L2.5：汉代郡县白名单（**已实现** @ 2026-04-18）

**数据源**：

- 郡名同时剥去 "X郡/X国/X尹/X内史/X冯翊/X扶风" 后缀（史记中多不带后缀）后并入 `KNOWN_COMMANDERIES`

1. 若《汉书》文本更新 → 重跑 `python3 kg/entities/scripts/extract_hanshu_dili.py`

- 自动提取有~5% 噪声（描述片段被误当县名），但只要该噪声不在 entity_index 的 place 集合里就不会影响分类结果

## 五·二、L5：并列地名传播（**已实现** @ 2026-04-18）

**规则**：在 `chapter_md` 正文中，两个 `〖=X〗` 标记之间若只有"、"或"，"（可含空白），则视为并列。对多个并列 place 构成的 peer 组，从已分类条目向未分类条目传播（多数决 ≥ 60%）。

**典型触发上下文**：
- `⟦◈攻⟧〖=铚〗、〖=酂〗、〖=苦〗、〖=柘〗` — 被攻取的城邑/县序列
- `封...于〖=X〗、〖=Y〗、〖=Z〗` — 封邑列表
- `〖=X〗、〖=Y〗、〖=Z〗之民` — 州郡列表

**迭代**：最多 3 轮传播，直到无更新。

**约束**：仅对当前为空字符串的条目生效；已分类条目不被改写。

**效果**（2026-04-18 首次启用）：发现 588 组并列序列，升级 151 个 place。

## 五·三、三家注注释（**已实现** @ 2026-04-18）

扫描 `corpus/shiji/史记集解三家注索隐正义.txt`，匹配 `X，Y名` / `X，Y名也` 格式的条目定义，累积到 L3 hints。

已支持的模式（`classify_places.py::SANJIA_PATTERNS`）：

| 注释模式 | 推断类别 |
|----------|----------|
| `X，山名` | 山脉 |
| `X，水名` / `X，湖名` / `X，泽名` / `X，海名` | 水域 |
| `X，县名` | 县 |
| `X，郡名` | 郡 |
| `X，乡名` / `X，亭名` | 乡里 |
| `X，邑名` | 城邑 |
| `X，关名` / `X，塞名` | 关隘 |
| `X，国名` | 国家 |

**典型命中**：
- "涿鹿，山名" / "空桐，山名" → 山脉
- "西陵，国名也" → 国家
- "洞庭，湖名" / "彭蠡，湖名" → 水域

**局限**：当某地同时有多重注释（如 "涿鹿，山名" 与 "涿鹿县" 并存），优先级规则可能取其一。如需更细的时代语境（史记/汉书），需进一步的规则。

- 若发现漏归的皇陵，追加白名单即可

### 7.2 X门 的歧义

- 城门（建筑）："东都门"、"北门"、"司马门"
- 关口（关隘）："龙门"、"雁门"（→ 郡）、"孟门"
- 当前全部留空。可在 L3 引入："大门之守"、"守〖=X门〗" 之类上下文消歧

### 7.3 X国（作为 place 出现）的处理

- 如果 `〖=X国〗` 出现，当前留空
- 规则草案：
  - `封...于〖=X国〗` → 县（汉代侯国）
  - `至〖=X国〗` / `入〖=X国〗` → 区域（泛指该国之地域）

### 7.4 X林 / X谷 / X沙

- 林：`桂林` = 郡、`桃林` = 地区、`上林` = 苑（建筑）
- 谷：`函谷` = 关隘、`鬼谷` = 山谷
- 沙：`博浪沙` = 具体点、`流沙` = 区域
- 全部留空；L2/L3 规则成熟后再处理

## 二、分类流水线（决策顺序）

分类脚本 `kg/entities/scripts/classify_officials.py` 按以下层级打分：

```
L1   显式白名单（三公/九卿/列卿/军职/爵位/宫廷/文学/师傅/外邦/上古/泛称）
     + 王号判定（X+王 且 X 是邦国/地名）
L2   章节上下文规则（018-021 侯者年表 → 爵位；110-111 匈奴传 → 外邦职）
L2.5 《汉书·百官公卿表》白名单（KNOWN_HAN_OFFICIALS，由 extract_hanshu_baiguan.py 自动提取）
L3   共现动词/语境规则（读 chapter_md）
     + 三家注注释（读 corpus/shiji/史记集解三家注索隐正义.txt）
L4   后缀启发式（默认兜底）
L5   并列官职传播（同列 〖;X〗、〖;Y〗 属同类）
```

首轮上线顺序：L1 + L4 + L5（基础） → L2.5（批量扩充）→ L3 → L2（章节上下文）。

## 八、L5：并列官职传播

**规则**：在 `chapter_md` 正文中，两个 `〖;X〗` 标记之间若只有"、"（可含空白），则视为并列。对多个并列 official 构成的 peer 组，从已分类条目向未分类条目传播（多数决 ≥ 60%）。

**典型触发上下文**：
- `〖;丞相〗、〖;御史大夫〗、〖;太尉〗` — 三公序列
- `〖;丞相〗、〖;太尉〗、〖;廷尉〗、〖;典客〗` — 中央高官序列
- `〖;左贤王〗、〖;右贤王〗、〖;左谷蠡王〗` — 匈奴官序列

**约束**：仅对当前为空字符串的条目生效；已分类条目不被改写。

## 九、已登记的疑难与待办

### 9.1 "王" 的歧义
- `X王`（X 是邦国/地名）→ `王号`
- 单字"王" → `泛称`（帝王泛称）
- `X王`（X 是谥号如 霸/文/武）→ 视条目而定，可能 `泛称` 或 `王号`

### 9.2 "侯" 的歧义
- `X侯` → `爵位`（汉代列侯）
- 单字"侯" → `泛称`
- "列侯"、"彻侯"、"关内侯" → `爵位`
- 谥号+侯（如"安侯"作为官/爵称）→ 需上下文

### 9.3 "相/将/尉/令" 的时代分化
- "相" 战国时期是中央首辅；汉初诸侯王国也设"相"（郡级长官） → `cat-sangong` OR `cat-junli`
- "尉" 可以是 `cat-military`（都尉/校尉）也可以是 `cat-xianli`（县尉）
- "令" 多数是 `cat-xianli`（县令），少数是 `cat-jiuqing`（如 "廷尉令"）

### 9.4 X大夫 的歧义
- "五大夫"、"公大夫"（爵名）→ `爵位`
- "大夫"（身份通称、古职）→ `泛称`
- "谏议大夫"、"光禄大夫" → `文学顾问` 或 `宫廷近侍`

### 9.5 单字官名的处理
- `侯/王/相/将/尉/令/君/公` 等单字被标为 official，优先按"泛称"或根据章节时代分化
- 首轮作为 `cat-generic` 兜底；后续用 L3 精细化

# SKILL 03j: 人名身份分类规则

> 为《史记》4,921 个 person 实体打上"身份类"二级分类（帝王/诸侯君主/将相/谋臣策士/学者文士/…），供 `docs/entities/person.html` 按类筛选。
>
> 原则：**规则沉淀 > 一次拍脑袋**。每发现一批误分类，提炼出规则并记录在本文档里，改进 `classify_persons.py`，重跑即可。
>
> **与 SKILL_03h/03i 完全对称的工作流**：L1 白名单 → L2 章节上下文 → L2.5 rulers.json → L3 共现动词/注释 → L4 后缀启发式 → L5 并列传播。
>
> **人名独有 alias 子工作流**：`extract_aliases_from_tags.py` 扫描全部 tagged.md 的 `〖@X|Y〗` 内联消歧 + `disambiguation_map.json` 章节级消歧 + `rulers.json` 别名字段 + 鲍捷私文档先秦称呼对照，合并产出新 `entity_aliases.json`（4 列结构：surface / type / canonical / refs）。

## 八、L5：并列/亲属传播

**规则**：在 `chapter_md` 正文中，两个 `〖@X〗` 标记之间若只有"、"（可含空白），则视为并列。对多个并列 person 构成的 peer 组，从已分类条目向未分类条目传播（多数决 ≥ 60%）。

**典型触发上下文**：
- `〖@荆轲〗、〖@豫让〗、〖@聂政〗` — 刺客序列
- `〖@申公〗、〖@辕固〗、〖@伏生〗` — 儒林序列
- `〖@邓通〗、〖@韩嫣〗、〖@李延年〗` — 佞幸序列

**约束**：仅对当前为空字符串的条目生效；已分类条目不被改写。

## 九、别名（alias）子工作流 ★ 人名独有

### 9.1 新数据结构

`entity_aliases.json` 从旧的 `{canonical: [alias, ...]}` 改为 **4 列表结构**：

```json
{
  "person": [
    {
      "surface": "昭王",
      "type": "person",
      "canonical": "秦昭王",
      "refs": [["005_秦本纪","20.1"], ["071_樗里子甘茂列传","3"]]
    },
    {
      "surface": "昭王",
      "type": "person",
      "canonical": "燕昭王",
      "refs": [["034_燕召公世家","17"]]
    },
    {
      "surface": "卫鞅",
      "type": "person",
      "canonical": "商鞅",
      "refs": [["068_商君列传","2"], ["005_秦本纪","49"]]
    }
  ]
}
```

**关键特性**：
- 同一 surface 按 canonical 拆分多行（歧义时）
- refs 记录该消歧适用的章节/段落
- 可通过 refs 快速定位原文、验证正确性

### 9.2 数据来源优先级

1. **tagged.md 的 `〖@X|Y〗` 内联消歧** ← 最权威（作者实际使用过，2264 对已存在）
2. `disambiguation_map.json` 的章节级短名→全名（71 章 644 条）
3. `kg/relations/rulers.json` 的 `别名` 字段（656 条君主）
4. `private/to鲍捷 史记里的人名.md` 的先秦称呼对照（人工整理的古书对照表，~100 条）
5. 旧 `entity_aliases.json` 手工维护（保底，586 条）

### 9.3 抽取脚本

`kg/entities/scripts/extract_aliases_from_tags.py`：

```
扫描 chapter_md/*.tagged.md
  对每个 〖@X|Y〗 记 (surface=X, canonical=Y, ref=(chapter, para))
合并 disambiguation_map.json
  对每章 {短名: 全名} → (surface=短名, canonical=全名, ref=(chapter, '*'))
合并 rulers.json
  对每条 ruler 的 aliases → (surface=alias, canonical=谥号, ref=[])
合并 private/to鲍捷 史记里的人名.md
  解析 "canonical：alias1、alias2（来源）" 行 → 多条记录
合并旧 entity_aliases.json
  作为保底，但标记 source='legacy'

输出：
  entity_aliases.json（新 4 列结构）
  entity_aliases.v1.bak.json（旧结构备份）
  alias_conflicts.json（同 surface 同 canonical 的冲突报告）
```

### 9.4 冲突处理

- **同 surface → 多 canonical**：正常（如"昭王"→3 种），保留为多行
- **同 (surface, canonical) → 多 refs**：合并 refs
- **rulers.json 与 tagged.md 冲突**：以 tagged.md 为准，rulers.json 的别名追加进 refs=[]（表示未在标注中出现，仅来自历史文献）
- **旧 entity_aliases.json 条目在新数据中找不到 canonical**：归入 `alias_conflicts.json`，需人工审

### 10.1 单字人名假阳性

"象""益""会""代""舍""段"等单字既是人名也是常见动词/副词/形容词。

### 10.2 "X君"歧义

- `信陵君/孟尝君/平原君/春申君/魏公子` → 宗室
- `商君/武安君/应侯/穰侯/文信侯` → 将相
- 需用 rulers.json 或白名单区分

### 10.3 "X侯"歧义

- 汉代列侯（开国功臣）→ 将相
- 春秋小国侯君（曹侯/许侯）→ 诸侯君主
- 按上下文与 rulers.json 决定

### 10.4 诸侯王兼任将相

部分诸侯王起家是将领（如韩信、英布、彭越），后被封王。
- 多标签：主标 `诸侯君主`（最终地位），次标 `将相`（起家身份）

### 10.5 待拆分

- `丞相何` = 萧何 + 丞相
- `卫将军青` = 卫青 + 卫将军
- `淮阴侯韩信` = 韩信 + 淮阴侯
- 归入 `cat-split`，源头需重新标注

- 两者在汉代均为列名诸侯国，与郡并立（郡国并行），应一并视为邦国

**多标签规则**：
- 允许一国多类（如 `秦` = `周代诸侯`（战国期）+`朝代`（统一后），按章节消歧；`代` = `秦末列国`+`汉诸侯王国`；`楚` = `周代诸侯`+`秦末列国`（西楚）+`汉诸侯王国`）
- 主标 = priority 最小的类
- 跨时代冲突通过章节上下文（L2）消歧

**"战国七雄"不单列的理由**：秦/楚/齐/燕/赵/魏/韩 均为周代诸侯沿续而来，战国阶段只是时间延续，从"政体性质"看仍属 `周代诸侯`。后续若需区分春秋/战国时段，由置信度标签或三级分类承担，不增设一级类。

**"外邦"不再细分外夷/西域**：《史记》115-116/123 列传并称"四夷/西域"，统治形态（有王、有都、有使臣）近似，合为一类更简洁。

**与地名 `cat-nation` 的边界**：
- place 类里的"国家"（大宛/大夏/朝鲜/南越…）与本 skill 的 `外邦` **高度重叠**
- 处置策略：同一 surface 既可以是 `◆邦国` 也可以是 `=地名`。feudal-state 侧关注"政体 + 统治者 + 国名互认"；place 侧关注"地理区域"
- 本 skill 只处理已被标为 `〖◆X〗` 的条目；`〖=X〗` 里的国家归 03h 管

### 4.2 侯者年表 → 汉侯国

汉代列侯的"侯国"是**邦国的一种**（列侯的封国 = 食邑封地）。若 feudal-state 条目的 refs 集中在 018-021 侯者年表，且不在 `EXPLICIT_HAN_VASSAL` 内 → `cat-han-marquis`（保留在 feudal-state，不迁移）。

#### 4.2.1 侯表第一列的强制规则（HT-01/02/03）

**HT-01 侯表第一列一律标邦国 + 消歧为"X侯国"**：018-021 四张侯者年表，第一列"国名"单元格中的封国名一律标为 `〖◆X|X侯国〗`，归入 `cat-han-marquis`。
- 显示文本保留原字（不改变原文字符），规范名统一为 `X侯国`（如 `便 → 〖◆便|便侯国〗`，`平阳 → 〖◆平阳|平阳侯国〗`）
- ❌ 不标为 `〖=X〗`（地名）—— 即便该县在国除后仍作地名存在
- ❌ 不标为 `〖@X〗`（人名）—— 即便封国名与某祖先/君主同名
- ❌ 不留裸字 —— 必须显式标记
- ❌ 不留无消歧的 `〖◆X〗` —— 必须带 `|X侯国` 规范名
- ✅ 迁徙封地（如 018 r15 酂 → 筑阳 → 武阳，出现在后续纪年格内）同样按 `〖◆X|X侯国〗` 处理

**HT-02 正文中同名串的消歧**：
- 作**封国/侯国**语境（"封 X 侯"、"X 侯某嗣"、"X 国除"）→ `〖◆X〗`
- 作**地理位置**语境（"起 X"、"至 X"、"定 X"、"⟦◈击⟧ X"）→ `〖=X〗`
- 同 surface 两 type 共存合法（与"秦"朝代/诸侯跨时代双标同理）

**HT-03 "X 侯" 的边界**：
- "为 X 侯"整体是封爵动作。封国名标 `〖◆X〗`，"侯"字保留为裸字或按语境处理
- "侯"单字作动词（封/为侯）用 `⟦○侯⟧`（见 feedback_hou_verb）
- 不要把封国+侯合并成 `〖;X侯〗`（职位）—— 职位是"列侯"，封国本身在侯前

**修复脚本**：`scripts/fix_houbiao_col1.py` 对 018-021 表格第一列批量将 `〖=X〗`/`〖@X〗`/裸字归一化为 `〖◆X〗`。

### 4.3 外邦四夷列传

- 110_匈奴列传：匈奴及其部落 → `cat-tribe-mis`（匈奴本身是部族非邦国）
- 113_南越/114_东越/115_朝鲜/116_西南夷：对应邦国 → `cat-foreign`
- 123_大宛列传：西域诸国 → `cat-foreign`

### 4.4 诸侯王年表 → 汉诸侯王国

## 九、误标识别（邦国独有三条子流程）★

朝代与合称在 §一 已确立为合法分类（`cat-dynasty` / `cat-collective`），不再视为误标。真·跨类型误标仅剩三条：

### 9.1 `cat-tribe-mis` — 部族误标为邦国

**判定条件**：
- 在 `EXPLICIT_TRIBE_MIS` 内（匈奴/戎/狄/荆蛮/犬戎/山戎/三苗/有苗 等）
- 或 rulers.json 类型 = `单于` 且所属国 ∈ {匈奴}

**源头修复**：`〖◆X〗 → 〖&X〗`（tribe 标签），批量交 **03e1 跨类型迁移**。

**边界说明**：
- 南越/东越/闽越/朝鲜/夜郎/滇 — 这些虽然是夷狄，但《史记》视为"国"（有王、有都城、有正式外交），归 `cat-foreign` 非 `cat-tribe-mis`
- 匈奴、戎、狄 — 司马迁视为"部族/游牧联盟"，归 `cat-tribe-mis`

**预期规模**：约 15-25 处（匈奴高频）。

### 9.2 `cat-place-mis` — 地理大区/郡名误标为邦国

**判定条件**：
- 在 `EXPLICIT_PLACE_MIS` 内（关中/山东/北地/河东/上郡/南郡/豫章/益州…）
- **注意**：汉代侯国不归 place-mis，而归 `cat-han-marquis`（侯国也是邦国）
- 只有纯地理大区（关中/山东/河东）和郡名（上郡/南郡）才归 place-mis

**源头修复**：`〖◆X〗 → 〖=X〗`（place 标签），批量交 **03e1 跨类型迁移**。

**预期规模**：约 10-20 处（去掉侯国后规模显著变小）。

### 9.3 `cat-split` — 复合邦国需拆分

**判定条件**：
- 含"X国"后缀且 X 本身已有 `〖◆X〗` 条目（秦国/齐国/燕国/楚国/赵国/魏国/宋国）— 与同名单字冗余
- 含邦国 + 王/主/君（齐王/楚王 — 应归 official 非 feudal-state）
- 源头误合的多国连写（若标注者未按合称录入而是糊成一整个 ◆ 标签）

**说明**：合法的合称（三晋/七国/齐秦楚赵）归 `cat-collective`，不进 split；split 专指**源头标注技术错误**（如漏切分、国 后缀冗余、与官职边界错位）。

**源头修复**：逐条拆分，人工确认。

**预期规模**：约 15-20 处。

# SKILL 06e: 概念分类树构建 — Bottom-Up 归纳与颗粒度调整

> **核心理念**：分类不是先验的，是从数据中归纳的。  
> 先有实例，再有类；先看数量，再定颗粒度。

---

## 一、何时使用

| 场景 | 信号 |
|------|------|
| 新一批实体已标注，需要建立分类体系 | 索引中有大量无分类实体 |
| 某叶子类实例数 > 50，内部有明显子结构 | 拆分信号：子结构可通过朝代/职能/地域切分 |
| 某叶子类实例数 < 10，且与邻类高度相关 | 合并信号：单独列类没有辨别力 |
| 分类树 MD 与 TTL 不一致 | 有人手工编辑了 MD，需要以 TTL 为准重生 |
| 需要补全缺失的实体（如某朝代帝王未入树） | 缺口分析发现高频实体未入树 |

**不适用**：从零设计一个全新实体类型的本体（用 SKILL_06a）。

## 二、Bottom-Up 构建流程（5步）

### Step 1. 实例统计与分桶

从 `entity_index.json` 提取目标实体类型，按出现频次分桶：

```bash
python kg/taxonomy/scripts/person_gap_report.py
```

| 频次桶 | 处理策略 |
|--------|---------|
| ≥ 50 | 必须入树；出现次数高说明文本中确实重要 |
| 20–49 | 必须入树 |
| 10–19 | 应入树 |
| 5–9 | 建议入树，上下文验证后加入 |
| 2–4 | 择优：确认非别名后加入 |
| 1 | 留待批量脚本处理；人工成本过高 |

**关键动作**：区分"真实新实例"与"别名"——后者不需要新分类条目，只需在 `entity_aliases.json` 建立映射。

### Step 2. 归纳初始分类

对 Step 1 筛出的高频实体，自底向上归纳分组。归纳信号按优先级：

1. **显式归属**：白名单（rulers.json / shihao_index.json）直接确定类别
2. **章节信号**：主要出现在专题列传（刺客/酷吏/货殖等）→ 直接对应类
3. **名称后缀**：单于/夫人/公子/太子 → 对应特定类
4. **共现模式**：与已知类成员高度共现 → 同类推断
5. **历史常识**：帝王世系表（如夏本纪17王、商本纪序列）→ 补全空白

**多信号原则**：至少两个独立信号才可信。单信号分类历史准确率约 12%（见 SKILL_06a §5 记录）。

### Step 3. 颗粒度调整

这是 06e 的核心步骤。**颗粒度信号**：

#### 拆分信号（leaf class 实例数 > 50）

当某叶子类超过 50 个实例，检查内部是否有可切分维度：

```
信号A：时间维度 — 早/中/晚期（如秦国历代君主：秦孝公前/商鞅变法后/统一后）
信号B：职能维度 — 文臣/武将/外交（如汉臣可拆）
信号C：地域维度 — 关中/山东/荆楚（如战国策士分布）
信号D：历史阶段 — 如"汉初"/"汉中后"已拆分
```

拆分阈值建议：
- 子类实例数 ≥ 10 → 值得单独列类
- 子类实例数 < 10 → 合入父类或"其他"桶

#### 合并信号（leaf class 实例数 < 10）

当叶子类过小，考虑：
- 合并到邻近类（功能相似、时代相近）
- 提升为父类的实例（不单独设子类）
- 保留但标注"稀疏类"（<10，可能扩充）

#### 实操判断表

| 现状 | 建议操作 | TTL 修改 |
|------|---------|---------|
| 某类 > 100 且内部异质性高 | 必须拆分 | 新建子类，移动实例 |
| 某类 50–100 且有清晰切分维度 | 建议拆分 | 同上 |
| 某类 10–50 | 保持，继续观察 | 只新增实例 |
| 某类 < 10，与邻类功能重叠 | 合并 | 改 rdf:type，删子类 |
| 某类 < 5，历史上确实独特 | 保留为稀疏类 | 加注释说明 |

### Step 4. TTL 追加与校验

**追加格式**：

```turtle
per:少康 a per:夏 ; rdfs:label "少康"@zh ; :count 8 .
per:帝槐 a per:夏 ; rdfs:label "帝槐"@zh ; :count 3 .
```

**校验三步**：

```python
# 4.1 语法
from rdflib import Graph
g = Graph(); g.parse('kg/taxonomy/person.ttl', format='turtle')
print(f'{len(g)} triples')  # 不报错即通过

# 4.2 冗余检查（重跑 gap report）
python kg/taxonomy/scripts/person_gap_report.py
# TTL 冗余 < 100 为合格

# 4.3 没有实例游离在父类（本级）中未入子类
```

### Step 5. 重生分类树 MD

```bash
python kg/taxonomy/scripts/build_taxonomy.py kg/taxonomy/person.ttl
# → kg/taxonomy/person_taxonomy.md
```

对应 HTML（如有）同步重跑：
```bash
python kg/taxonomy/scripts/rebuild_person_tree_html.py
```

## 三、颗粒度设计原则

### 垂直粒度（层次深度）

| 层级 | 示例（人物树） | 原则 |
|------|-------------|------|
| L0 | 人物 | 顶层锚点，不挂实例 |
| L1 | 王室 / 臣 / 诸子百家 | 大类，<100 类覆盖全域 |
| L2 | 帝王 / 诸侯 / 后妃 / 宗室 | 中类，每类 20–200 实例 |
| L3 | 夏 / 商 / 周 / 汉 | 叶类，每类 10–80 实例 |
| L4 | （仅当 L3 > 80 才拆） | 如"汉初"/"汉中后" |

**原则**：树深不超过 4 层；实例只挂在叶节点。

### 水平粒度（同层类数）

- 同一父类下子类数量建议 3–12 个
- < 3 个说明粒度太粗（考虑下移）
- > 15 个说明粒度太细（考虑合并或引入中间层）

### 正确案例（汉代帝王拆分）

```
汉（帝王）→ 汉（5人，高祖/惠帝/文帝/景帝/武帝等）
```
汉代帝王本可单独列出每一任，但 史记 时段只到武帝，所以合并为一类（约 10 人）是合适颗粒度。

### 反例（过细导致空类）

```
# 错误：为 1-2 人建类，无扩充空间
per:帝皋 a owl:Class ; rdfs:subClassOf per:夏 .  # ❌ 太细
```

正确做法：1-3 人的小类直接挂在父类下作为实例，不单独建子类。

## 四、缺口补全工作流

当发现某朝代/某类别大量缺失（如夏朝帝王）：

1. **查历史序列**：从史书（如夏本纪）获取完整列表
2. **比对索引**：`entity_index.json` 中查找各名称的出现频次
3. **频次筛选**：≥ 3 次出现的必须入树
4. **别名去重**：同一人的多种称谓只建一个 TTL 实例
5. **TTL 追加**：按频次排序插入
6. **重生 MD**：运行 `build_taxonomy.py`

**夏朝补全示例**（已实施）：

| 帝王 | 在史记中的名称 | 索引频次 | 状态 |

# SKILL 06a: 实体到本体管线 — 从标注文本到 RDF 分类本体

> 从《史记》标注实体出发，构建 OWL/RDF 本体的完整工作流。以生物类（388 种）为首个实例。

---

## 一、管线概览

```
chapter_md/*.tagged.md     标注文本（18类实体标记）
        ↓ build_entity_index.py
kg/entities/data/entity_index.json    实体索引（按类型+出现次数+章节引用）
        ↓ 人工/LLM 分类
kg/{type}/data/{type}_wordlist.json   分类词表（多层分类树 + 歧义标记）
        ↓ 脚本生成
kg/{type}/data/{type}_taxonomy.md     可读分类树（Markdown）
        ↓ 脚本生成
kg/taxonomy/{type}.ttl                OWL/RDF 本体（类+实例+属性）
```

**核心原则：** 本体不是凭空设计的，而是从标注实例中逐层归纳涌现。

---

## 二、步骤详解

### Step 1. 从实体索引中提取类型词表（含词条简介）

**输入**：`entity_index.json` 中某个类型的全部条目

**操作**：按出现次数排序，人工审视词条，归纳分类维度

**关键步骤：为每个词条生成简介**

词表不应只是词条列表——每个词条应附带一个从上下文自动提取的简介（1-2句话），描述此实体是什么、做了什么。这个简介在后续本体分类阶段极其有用：

```json
{
  "韩信": {
    "count": 333,
    "summary": "汉初将领，助刘邦灭项羽，封齐王/楚王，后被吕后杀于长乐宫",
    "chapters": ["008_高祖本纪", "092_淮阴侯列传"]
  },
  "管仲": {
    "count": 77,
    "summary": "齐桓公相，辅佐齐桓公称霸，主张尊王攘夷",
    "chapters": ["032_齐太公世家", "062_管晏列传"]
  }
}
```

**为什么简介很重要：**

在人物本体构建中，我们遇到了反复的分类困难：
- 韩信（333次）主要出现在高祖本纪 → 按章节分应归"本纪臣子"，但他实际是"将领"
- 司马相如（104次）主要出现在列传 → 按章节分应归"将相"，但他实际是"文学家"
- 赵高（139次）主要出现在秦始皇本纪 → 按章节分应归"本纪臣子"，但他实际是"佞臣/宦官"

如果在词表阶段就有简介 `"汉初将领，封齐王"` / `"辞赋家，作子虚赋"` / `"秦宦官，指鹿为马"`，本体分类就可以直接基于语义而非章节位置。

**简介生成方法：**
1. 从 `entity_index.json` 提取每个实体的所有出现上下文（±15字）
2. 用 LLM 从上下文中总结一句话简介
3. 或：从章节标题 + 共现的身份词（`〖#〗`）/ 官职词（`〖;〗`）自动拼接

**管线升级：词表 → 带简介的词表 → 分类树**

```
entity_index.json
    ↓ Step 1a: 提取词表
wordlist.json (词条 + 出现次数)
    ↓ Step 1b: 生成简介（LLM或规则）
wordlist_with_summary.json (词条 + 次数 + 简介)
    ↓ Step 2: 基于简介归纳分类
taxonomy.md → person.ttl
```

这是从人物本体构建实践中发现的关键方法论改进：**词表阶段的简介投资，在本体分类阶段获得十倍回报**。

**输出**：`{type}_wordlist.json`（三层结构，可扩展简介字段）

```json
{
  "always_{type}": {
    "category_1": ["word_a", "word_b"],
    "category_2": ["word_c", "word_d"]
  },
  "context_dependent": {
    "type_vs_other": { "word_x": "判断说明" }
  },
  "new_candidates": { ... }
}
```

**生物类实例**：
```json
{
  "always_biology": {
    "animals_domestic": ["马", "牛", "羊", "狗", "鸡", "豕"],
    "animals_wild":     ["虎", "鹿", "兔", "狼", "豹"],
    "birds":            ["鸟", "雉", "燕", "鸿鹄"],
    "fish_aquatic":     ["鱼", "鳖", "鼋"],
    "insects":          ["蝗", "蛇", "蜂"],
    "plants_crops":     ["稻", "黍", "稷", "菽", "麻"],
    "plants_trees":     ["桑", "松", "柏", "竹"],
    "plants_herbs":     ["兰", "芝", "椒"]
  },
  "context_dependent": {
    "biology_vs_mythical": { "龙": "天降龙=生物; 龙颜=比喻" },
    "biology_vs_metaphor": { "虎狼": "虎狼心=比喻; 手搏虎狼=生物" }
  }
}
```

### Step 2. 设计分类树（类层次）

**类名命名原则：**

1. **自明性** — 类名必须一目了然，不需要依赖树结构上下文来理解。
   - ✗ `燕 [7人]` — 是诸侯/燕国？还是臣/春秋/燕？
   - ✓ `燕国臣子 [7人]` — 清晰无歧义

2. **无歧义** — 同名不能出现在不同父类下。如"齐"在春秋和战国下各出现一次，必须改为"齐国臣子(春秋)"和"齐国臣子(战国)"，或合并。

3. **语义完整** — 子类名应包含父类语义。不要用 `将` `相`，用 `秦国将领` `秦国相臣`。

4. **用中文** — URI 和标签都用中文，避免拼音碰撞（Han=汉≠韩）。

**方法**：从词表的分类维度出发，构建 3-4 层的类层次。

**设计原则**（对应 Ontology 101 Step 4）：

1. **自底向上** — 从实例归纳类，不从理论推演类
2. **中间层最丰富** — 顶层（动物/植物）过粗，底层（单个物种）过细，中间层（家畜/野兽/鸟类）承载分类信息
3. **允许集合类** — 古文中"六畜"、"五穀"、"鸟兽"等是独立概念，不归入动物或植物，单列"集合泛称"类
4. **神话类单列** — 龙、凤、麒麟等跨越生物/神话边界，单设"神话动物"子类

**生物类分类树**：

```
LivingThing (生物)
├── Animal (动物)
│   ├── Domestic (家畜)
│   │   ├── Equine (马属) — 马(102), 驹(9), 骥(5)...
│   │   ├── Bovine (牛属) — 牛(36)
│   │   ├── Ovine (羊属) — 羊(26)
│   │   ├── Canine (犬属) — 狗(32), 犬(4)
│   │   ├── Poultry (禽属) — 鸡(8)
│   │   └── Swine (猪属) — 彘(5), 豕(2)
│   ├── WildBeast (野兽) — 虎(23), 鹿(19), 熊(8)...
│   ├── Bird (鸟类) — 鸟(19), 雉(6)
│   ├── Aquatic (鱼类水族) — 鱼(33), 鳖(3)
│   ├── Insect (虫类) — 蛇(4), 蝗(3)
│   └── MythicalAnimal (神话动物) — 龙(9), 凤皇(6)
├── Plant (植物)
│   ├── Grain (穀物) — 稻(4), 禾(4)
│   ├── Tree (树木) — 木(23), 桑(7)
│   ├── Herb (草本花卉) — 兰(9), 芝(4)
│   └── FruitVeg (果蔬) — 橘(3), 枣栗(3)
└── Collective (集合泛称) — 草木(14), 鸟兽(10)
```

### Step 3. 生成可读分类树（Markdown）

**输出**：`{type}_taxonomy.md`

脚本从 `entity_index.json` + 分类规则自动生成，格式：

```markdown
## 动物
### 家畜
#### 马属（33 种，162 次）
- 马（102）
- 驹（9）
- 骥（5）
...
```

每种实体列出出现次数，按次数降序排列。

### Step 4. 生成 RDF/OWL 本体（Turtle）

**输出**：`kg/taxonomy/{type}.ttl`

**命名约定**：
- 命名空间：`http://memect.cn/baojie/ontologies/2025/1/shiji/biology/`
- 类名：ASCII 英文（`bio:Equine`），中文放 `rdfs:label`
- 实例名：`bio:i_{pinyin}`（如 `bio:i_ma`），中文放 `rdfs:label`
- 属性：`:count`（出现次数）

**Turtle 模式**：

```turtle
bio:Equine a owl:Class ;
    rdfs:subClassOf bio:Domestic ;
    rdfs:label "马属"@zh, "Equine"@en .

bio:i_ma a bio:Equine ;
    rdfs:label "马"@zh ;
    :count 102 .
```

**验证**：用 `rdflib` 解析确认语法正确。

```python
from rdflib import Graph
g = Graph()
g.parse('kg/taxonomy/biology.ttl', format='turtle')
print(f'{len(g)} triples, {n_classes} classes, {n_instances} instances')
```

### Step 5. 反思验证（Reflection）

**自动分类必须经过反思验证。** 初次分类的错误率可能极高——人物帝王类首次分类437人中仅49人正确（88%误分率）。

**反思方法：逐类审查**

对每个分类类别，列出所有实例，逐一检查是否符合该类的定义：

```
帝王类反思流程：
1. 列出所有被分类为"帝王"的人物（437人）
2. 对每个人，检验分类信号：
   - 是否在帝王名册中？（明确帝王名）
   - 名称是否匹配帝号模式？（X帝/X祖/X王）
   - 是否为本纪标题人物？
3. 三个信号均不满足 → 判定为误分类
4. 分析误分原因 → 发现规则缺陷 → 修正规则
```

**误分根因分析（以帝王类为例）**：

| 误分原因 | 数量 | 示例 | 修正 |
|---------|------|------|------|
| "主章=本纪"≠"此人是帝王" | 384人 | 韩信主出现在高祖本纪 → 被误分为帝王 | 改用帝王名册+名称模式 |
| 单信号分类不可靠 | — | 仅凭章节信号，准确率仅12% | 多信号叠加 |

**反思产生的分类规则升级**：

```
v1（首次）: 主章为本纪 → 帝王          准确率 12%
v2（反思后）: 帝王名册 ∪ 帝号模式 ∪ 本纪标题人物  准确率 ~95%
```

**反思轮次示例（人物本体，10+轮）**：

| 轮次 | 类 | 修正 | 发现 |
|------|---|------|------|
| 1 | 帝王 | 437→49人 | "主章=本纪"≠帝王（韩信等臣子被误分），准确率仅12% |
| 2 | 帝王 | 49→90人（含子类修正） | 秦国诸侯≠秦朝帝王；周公旦是摄政非天子 |
| 3 | 诸侯 | 609→432人 | 世家中提到的帝王/诸侯/后妃不应重复归入 |
| 4 | 臣子类 | — | "主章世家"≠所属国（韩康子出现在魏世家因三家分晋叙事） |
| 5 | 臣·强制拆分 | 20+人叶子类全部拆分 | 晋国臣子→六卿/世族/宗室/将领/卿大夫/谋臣 |
| 6 | 子类实例审查 | 多处修正 | 吴楚臣子混入国王（白公/平王）；汉初诸将混入诸侯（黥布/魏豹） |
| 7 | 外邦审查 | 5+人移出 | 匈奴/大宛西域混入汉人（张骞/赵破奴） |
| 8 | 中间层设计 | 引入王室/诸子百家/社会人物分组 | 合并诸侯重臣+将相→臣；功臣侯爵归入臣 |
| 9 | (本级)清理 | 多处修正 | 帝武乙/帝太丁残留商代(本级)而非商帝王 |
| 10 | 类名规范化 | 全面修正 | 拼音URI碰撞(Han=汉=韩)→改用中文URI |

**详细过程记录**：见 `doc/methodology/人物本体构建过程.md`

**通用反思原则**：

1. **高频实例优先审查** — 出现次数最多的实例最容易暴露分类错误
2. **单信号不可靠** — 至少两个独立信号叠加才可信（章节+名称、章节+共现）。人物帝王类仅凭章节信号准确率仅12%
3. **误分析产出规则** — 分析"为什么错"比"哪些错"更重要，它能改进分类规则
4. **先审大类后审小类** — 大类（帝王437→90人）的修正幅度远大于小类（刺客17人基本正确）
5. **保留"其他"类** — 无法分类的实例放入"其他"，不强行归类
6. **区分分组维度与语义断言** — "按主要出现章节分组"是数据组织方式，不是"此人属于该国"的语义断言。子类标签应注明是分组还是断言
7. **历史语境影响分类** — 同一政体在不同时期有不同性质（秦国=诸侯，秦朝=帝国），分类必须考虑时间维度
8. **拆分后必须清理(本级)残留** — 每次拆分子类后，检查是否有实例被遗忘在父类的"本级"中
9. **章节信号 ≠ 所属国家** — 跨国叙事（三家分晋、合纵连横、出使征战）导致人物出现在非本国章节
10. **逐一审查子类实例** — 每次拆分出子类后，必须逐一检查实例归属是否正确（国王混入臣子、汉人混入外邦等）

### Step 6. 迭代优化

**常见迭代**：

1. **合并过细的类** — 如果某个叶子类只有 1-2 个实例，考虑合并到父类
2. **拆分过粗的类** — 如果某个类超过 50 个实例且内部有明显子群，考虑拆分
3. **处理多归属** — 某些实体可归入多个类（如"蛟龙"可归鱼类或神话），选择主要归属，在 `rdfs:comment` 中注明
4. **补充属性** — 除 `:count` 外，可添加 `rdfs:comment`（典故/来源说明）、`rdfs:seeAlso`（关联章节）

## 三、分类判断的难点

### 3.1 生物 vs 神话

| 词 | 用法 | 归类 |
|----|------|------|
| 龙 | "天降龙" → 实际出现 | 神话动物 |
| 龙 | "龙颜" → 比喻 | 不标注 |
| 凤皇 | "凤皇来翔" → 祥瑞 | 神话动物 |
| 白鹿 | "获白鹿" → 实际猎获 | 野兽 |

### 3.2 集合 vs 具体

"六畜"不等于马+牛+羊+鸡+犬+豕的并集。它是一个独立的语义概念（"六畜兴旺"），应作为独立实例归入"集合泛称"类。

### 3.3 跨类型实体

| 词 | 生物类标注 | 其他类型标注 | 说明 |
|----|-----------|------------|------|
| 白云 | `〖+白云〗` | — | 实为地名或天文，误标 |
| 犀象 | `〖+犀象〗` | — | 集合泛称 |
| 苍狗 | `〖+苍狗〗` | — | 实为天文（白衣苍狗） |

这些需要在分类时修正，或移到正确的实体类型。

### 3.4 人物分类的典型错误模式

从 10+ 轮反思中总结的七种反复出现的错误模式：

| 错误模式 | 说明 | 防范方法 |
|----------|------|---------|
| **章节信号误导** | 人物出现在某章 ≠ 属于该章的类别（韩信→帝王） | 多信号叠加验证 |
| **国王混入臣子** | 拆分后未逐一审查（白公→吴楚臣子） | 拆分后逐一检查 |
| **汉人混入外邦** | 跨国叙事信号误导（张骞→匈奴） | 区分叙事语境与归属 |
| **类名歧义** | "燕"不明确是诸侯/燕还是臣/燕 | 类名自明原则 |
| **平铺非嵌套** | 子类显示为同级而非子级 | 递归渲染器+审查 |
| **(本级)残留** | 拆分后遗忘在父类的实例 | 拆分后检查本级 |
| **URI碰撞** | 拼音 Han=汉=韩 | 全部使用中文URI |

### 待建本体（按优先级）

1. **地名** — 1,800+ 实体，可按地理类型（城邑/山/川/关隘）分类
2. **官职** — 2,100+ 实体，可按朝代/级别/文武分类
3. **器物** — 1,000+ 实体，可按功能（礼器/兵器/车马/货币）分类

### 人物本体的特殊之处

人物本体与生物本体有两个关键差异，形成了新的方法论模式：

**差异一：实例 vs 类型**

生物本体中，"马"既是类（马属），也是实例（出现102次的词条）。人物本体中，每个人（刘邦、项羽）都是纯粹的实例，分类（帝王、将相、刺客）是后归纳的。

| | 生物 | 人物 |
|---|---|---|
| 类的来源 | 词表中预设（animals_domestic等） | 从章节标题和出现模式归纳 |
| 实例的来源 | 标注提取的物种名 | 标注提取的人名 |
| 类-实例关系 | 1:1（马 → 马属） | 1:N（项羽 → 帝王 + 将相） |

**差异二：多重分类**

人物天然具有多重身份。10.6% 的高频人物属于两个以上分类：

| 人物 | 分类 |
|------|------|
| 项羽 | 帝王 + 将相 |
| 李斯 | 法家 + 将相 |
| 吕不韦 | 商贾 + 将相 |
| 吕太后 | 后妃 + 帝王 |

在 RDF 中用 `a per:Emperor , per:GeneralMinister` 表达多类型。

**差异三：分类信号来自章节结构**

史记的体例本身就是一种分类系统：本纪（帝王）、世家（诸侯重臣）、列传（各类人物）。列传标题直接给出人物类型："刺客列传"→刺客类，"游侠列传"→游侠类。这是古籍本体构建特有的信号来源——文献体例即分类学。

**分类方法论：三层信号叠加**

1. **章节信号**：主要出现章节的体裁/标题（最强信号）
2. **名称模式**：人名后缀（X帝/X太后/X公 → 帝王/后妃/诸侯）
3. **共现信号**：与身份词（`〖#〗`）、官职词（`〖;〗`）的共现关系（待实现）

## 五、工具链

| 工具 | 用途 |
|------|------|
| `build_entity_index.py` | 从标注文本提取实体索引 |
| `build_taxonomy.py` | 从 TTL 本体生成 Markdown 分类树（通用，适用于任意实体类型） |
| `rdflib` (Python) | Turtle 语法验证和查询 |
| Protege | 可视化浏览/编辑本体（可选） |
| `git diff` | 跟踪本体变更（Turtle 是纯文本，diff 友好） |

### build_taxonomy.py 用法

```bash
# 基本用法：TTL → 同名_taxonomy.md
python kg/taxonomy/scripts/build_taxonomy.py kg/taxonomy/person.ttl
python kg/taxonomy/scripts/build_taxonomy.py kg/taxonomy/biology.ttl

# 指定输出路径和单位
python kg/taxonomy/scripts/build_taxonomy.py kg/taxonomy/person.ttl -o kg/taxonomy/person_taxonomy.md --unit 人

# 自定义顶层子类排列顺序
python kg/taxonomy/scripts/build_taxonomy.py kg/taxonomy/person.ttl \
  --order "王室,臣,策士,诸子百家,社会人物,方术,外邦,虚构人物,疑似误标"

# 调整每类最多显示的实例数
python kg/taxonomy/scripts/build_taxonomy.py kg/taxonomy/person.ttl --max-show 30
```

**设计原则**：TTL 本身是权威数据源，不需要额外的 JSON 分类数据。脚本从 TTL 中解析 `owl:Class` + `rdfs:subClassOf`（类层次）、`a <class>`（实例归类）、`rdfs:label`（中文标签）、`:count`（出现次数），自动生成可读的 Markdown 分类树。

## 七、实战案例：人物本体（10轮反思详录）

> 完整过程记录见 `doc/methodology/人物本体构建过程.md`。以下为方法论精华摘要。

### 7.1 规模与难度

从1,825个人名实体出发，经10+轮反思，构建142类、~5,826三元组的OWL/RDF人物本体。与生物本体的关键差异：

| | 生物（先行试验） | 人物 |
|---|---|---|
| 类的来源 | 词表预设（动物/植物） | 需从实例中归纳 |
| 实例-类关系 | 1:1 | 1:N（韩信→将领+臣） |
| 分类信号 | 词义本身 | 章节位置+名称模式+历史知识 |

### 7.2 反思迭代轨迹

| 轮次 | 操作 | 关键发现 |
|------|------|---------|
| 1 | 章节信号初始分类 | 帝王类88%误分（437→49人，准确率12%） |
| 2 | 三信号叠加修正帝王 | 437→90人，秦国诸侯≠秦朝帝王 |
| 3 | 诸侯类排除法 | 609→432人，帝王/后妃不重复归入 |
| 4 | 臣类展开（最大挑战） | 800+人，采用`时代×国家×性质`三维拆分 |
| 5 | 叶子类强制拆分 | 所有20人以上叶子类继续拆分 |
| 6 | 中间层与顶层调整 | 引入王室/诸子百家/社会人物分组 |
| 7 | URI与命名规范 | 拼音碰撞（Han=汉=韩），全改中文URI |
| 8 | (本级)残留清理 | 每次拆分后检查父类遗留实例 |
| 9 | 格式演进 | pickle→JSON→TTL，脚本抽象化 |
| 10 | 收敛验证 | 剩余问题集中在20-50人叶子类 |

### 7.3 典型错误模式（可复用于其他实体类型）

| 错误模式 | 频次 | 示例 | 防范方法 |
|----------|------|------|---------|
| **章节信号误导** | 50+ | 韩信→帝王（因出现在本纪） | 多信号叠加验证 |
| **国王混入臣子** | 10+ | 白公胜→吴楚臣子（实为楚国君主） | 拆分后逐一审查 |
| **汉人混入外邦** | 5+ | 张骞→匈奴（因出现在匈奴列传） | 区分叙事场景与所属 |
| **诸侯混入将领** | 5+ | 黥布→汉初诸将（实为楚汉诸侯） | 身份优先于出场角色 |
| **类名歧义** | 10+ | "燕"→燕国诸侯 or 燕国臣子？ | 类名必须自明 |
| **(本级)残留** | 10+ | 拆分后遗忘在父类的实例 | 每次拆分后检查本级 |
| **拼音URI碰撞** | 1 | Han=汉=韩 | 用中文URI |

### 7.4 关键方法论

1. **单信号分类灾难性不可靠**。帝王类仅凭"主章=本纪"分类，准确率12%。至少需要两个独立信号叠加验证。

2. **分类从边缘案例中涌现**。不是先设计分类树再填充，而是实例的误分暴露规则缺陷，修正规则→改进分类树。

3. **反思收敛**。每轮发现的问题越来越少。10轮后，剩余问题集中在需要词条简介才能判断的叶子类。

4. **章节信号 ≠ 所属国家**是最大陷阱。跨国叙事（三家分晋、出使匈奴）导致人物出现在非本国章节。

5. **拆分后必须清理(本级)残留**。每次拆分子类，必须检查是否有实例被遗忘在父类。
