````text
# SKILL 07c: 反常推理 — 不符合常识的事实检测与解读

> 从《史记》文本中识别"反常事实"：单条记载本身没有矛盾，但违反常识、违反制度规则、或在当时语境下极为罕见。目标是发现值得深究的历史异常点。

**定位**: 异常检测器 — 快速扫描识别值得深究的异常点，输出研究线索清单。

**与相关SKILL的区别**:
- **vs SKILL_07 矛盾检测**: 矛盾检测关注**两处记载互相打架**；反常推理关注**单条记载本身令人意外**
- **vs SKILL_07e 真实性推理**: 反常推理只做**异常识别+初步分类**；真实性推理做**深度可信度评估+真伪判断**

**工作流程**:
```
SKILL_07c (反常推理) → 输出异常清单 → SKILL_07e (真实性推理) → 输出可信度评级
      ↓                                              ↓
 "这很奇怪"                                    "这是真是假？"
```

## 一、反常类型分类

### 1.1 数字反常

| 子类型 | 判断标准 | 典型案例 |
|--------|---------|---------|
| **兵力异常** | 单支军队超过50万，或双方兵力差距>10:1 | 长平之战赵军四十余万降卒 |
| **年龄异常** | 人物记载行为时年龄超出生理极限或常规 | 廉颇八十余岁仍欲为将 |
| **时间异常** | 事件发展速度违反地理/行军常识 | 数日内跨越千里 |
| **财富异常** | 赏赐/财富数量超出当时国家财政常规 | 陶朱公三致千金 |

### 1.2 行为反常

| 子类型 | 判断标准 | 典型案例 |
|--------|---------|---------|
| **身份越轨** | 庶民/女性/奴隶做了通常只有贵族/男性/自由人才能做的事 | 吕后临朝称制 |
| **亲情反常** | 父杀子、子弑父、手足相残且无明显动机 | 晋献公杀申生 |
| **忠奸反转** | 被《史记》正面评价的人物做了反道德的事，或反之 | — |
| **动机缺失** | 重大行为找不到合理动机，或现有解释自相矛盾 | — |

### 1.3 制度反常

| 子类型 | 判断标准 | 典型案例 |
|--------|---------|---------|
| **礼制违反** | 行为违反当时已知周礼/汉制的明文规定 | 诸侯僭用天子礼乐 |
| **继承异常** | 世系/王位继承跳过通常规则（嫡长子制等）且无记载原因 | — |
| **封赏异常** | 封号/爵位/赏赐规格与功绩明显不相称 | — |
| **刑罚异常** | 同类罪行处置轻重悬殊 | — |

### 1.4 叙事反常

| 子类型 | 判断标准 | 典型案例 |
|--------|---------|---------|
| **沉默异常** | 重要人物/事件在相关章节完全缺席（应有而无） | 秦始皇无皇后记载 |
| **详略失衡** | 次要事件大书特书，重要事件一笔带过 | — |
| **评价矛盾** | 太史公曰与正文叙事传递出相反的态度 | — |
| **时序倒置** | 叙述顺序与事件时序明显不符且无明显原因 | — |

## 二、检测流程

```
结构化数据（实体+事件+关系+本体规则）
    ↓ 加载常识库规则
史记常识库 (kg/common-sense/)
    ↓ 规则扫描（数字阈值/制度违反/关系缺失）
候选反常清单
    ↓ LLM评估（是真反常？还是有常见解释？）
有价值的反常列表
    ↓ 分类标注（类型 + 置信度 + 可能解释）
输出：anomaly_report.json + 研究线索
```

**常识库支撑**: 反常检测依赖 [史记常识库](../kg/common-sense/) 提供的基准规则：
- 数字常识: 人口、兵力、年龄、财富、距离的合理范围
- 制度常识: 爵位、官职、礼制、继承、刑罚的规范
- 社会常识: 等级、性别、宗法的惯例
- 军事常识: 兵力、战术、行军的规律
- 其他: 时间、地理、经济、文化等10大类常识

### 2.1 规则检测（可自动化）

| 规则 | 数据源 | 输出 |
|------|--------|------|
| 军队规模 > 阈值 | 事件索引 `count` 字段 | 候选异常 |
| 人物年龄 > 80 且仍有军事行动 | 生卒年推断 + 事件 | 候选异常 |
| 嫡长子未继位 且无废嫡记载 | 世系关系 + 继承事件 | 候选异常 |
| 重要人物（出现频次>N）无死亡事件 | 实体索引 + 事件索引 | 候选异常 |

### 2.2 LLM评估提示词框架

```
你是一位审视《史记》异常事实的历史学助手。

已知事实：[原文引用]
所属章节：[篇名]
类型标注：[数字反常 / 行为反常 / 制度反常 / 叙事反常]

常识基准：[从 kg/common-sense/ 中引用相关常识]
示例：
- 若为数字反常：引用"单支军队常规规模: 5-20万"
- 若为制度反常：引用"嫡长子继承规则"
- 若为年龄反常：引用"将领出征年龄上限: 通常<65岁"

请判断：
1. 这条记载是否违反[常识/制度/逻辑]？（是/否/存疑）
2. 违反了哪条具体常识？（引用常识库编号，如 [1.1 人口与兵力规模]）
3. 有无通常的历史学解释？（列出1-3条）
4. 若无合理解释，这是否值得深入研究？（高/中/低价值）
5. 推荐追问方向：（一句话）
```

## 七、常识推断方法 (Meta-Skill: 反思迭代)

> **核心思想**: 从具体案例中归纳普适性规律,通过反思迭代不断完善常识库。

### 7.1 常识提取流程 (反思迭代)

```
【第1轮：案例收集】
├─ 输入: 已完成的反常检测案例 (如长平之战、廉颇老矣)
├─ 提问: "这些案例违反了什么共同的规律?"
└─ 输出: 候选常识条目列表

【第2轮：普适性检验】
├─ 输入: 候选常识条目
├─ 提问: "这条规律是否适用于多个案例?"
│         "这条规律是否有明确的时代边界?"
│         "这条规律是否可量化/可验证?"
├─ 反思:
│   ✅ 若适用于3+案例 → 保留
│   ✅ 若有时代标注 → 保留
│   ✅ 若可量化 → 保留
│   ❌ 若仅适用单一案例 → 丢弃
│   ❌ 若无法验证 → 标记为"推测性"
└─ 输出: 精炼后的常识条目

【第3轮：来源标注】
├─ 输入: 精炼后的常识条目
├─ 提问: "这条常识的数据来源是什么?"
│         "置信度如何评估?"
├─ 行动: 标注来源(出土文献/传世典籍/学界共识/统计归纳)
│         标注置信度(高/中/低)
└─ 输出: 规范化常识条目

【第4轮：规则化编码】
├─ 输入: 规范化常识条目
├─ 提问: "如何将这条常识转化为可自动检测的规则?"
├─ 行动:
│   - 数字类常识 → 阈值规则 (如"单支军队 > 50万 → 异常")
│   - 制度类常识 → 违规规则 (如"嫡长子未继位 且 无废嫡记载 → 异常")
│   - 关系类常识 → 缺失规则 (如"君主 无 配偶关系 → 异常")
└─ 输出: 可执行的检测规则

【第5轮：实战验证】
├─ 输入: 可执行的检测规则
├─ 行动: 在全部130篇《史记》中批量扫描
├─ 提问: "这条规则产生了多少候选异常?"
│         "假阳性率是多少?"
│         "是否需要调整阈值或条件?"
├─ 反思:
│   ✅ 若假阳性<20% → 规则有效,录入常识库
│   ⚠️  若假阳性20-50% → 调整阈值,重新验证
│   ❌ 若假阳性>50% → 规则失效,重新设计
└─ 输出: 验证后的常识库条目

【第6轮：持续更新】
├─ 输入: 新的研究成果、考古发现、案例分析
├─ 提问: "现有常识是否需要修正?"
│         "是否有新的常识需要补充?"
├─ 行动: 定期审核 (季度/年度)
└─ 输出: 更新后的常识库版本
```

  - 巨鹿之战: 秦军数十万
  - 垓下之战: 项羽军10万,汉军数十万
  - 井陉之战: 韩信数万,赵军20万
- 归纳规律: "单支军队常规规模 5-20万,超过30万为异常大军"

- 时代边界: 先秦至汉

# SKILL 07e: 真实性推理 — 可信度评估与真伪判断

> 在史源溯源（SKILL_07d）的基础上，运用多维度推理方法评估《史记》记载的可信度和真实性。

---

## 一、核心问题

**这个记载是真是假？**

在已知史源类型和传播链的前提下，进一步判断：
- 这个史源本身是否可信？
- 记载内容是否符合逻辑？
- 是否存在矛盾和反常？
- 谁是受益者？谁有动机伪造？
- 综合判断：这是真相还是谣言？

**本SKILL的界限**：
- ✅ **关注**：史源可信度、记载真实性、逻辑自洽性、动机分析
- ⚠️ **前提**：需要先使用SKILL_07d完成史源溯源
- ❌ **不关注**：史源是什么、传播链如何（已由SKILL_07d完成）

**与SKILL_07c的关系**：
- **SKILL_07c (反常推理)**：异常检测器，批量扫描识别"这很奇怪"的记载，输出异常清单
- **SKILL_07e (真实性推理)**：深度分析器，针对重大疑案判断"这是真是假"，输出可信度评级
- **工作流**：07c可为07e提供研究线索，07e也可独立使用（用户直接提问）

---

## 二、可信度评级体系

### 2.1 A-E五级评分

| 等级 | 定义 | 史源+真实性 | 典型特征 |
|------|------|-----------|---------|
| **A** | 高度可信 | 明确档案+多源验证+逻辑自洽 | 官方档案、亲历者口述、无矛盾 |
| **B** | 较为可信 | 家传口述+时间近+逻辑合理 | 传承链清晰、符合常理、核心事实可信 |
| **C** | 存疑 | 时间远或细节可疑+部分逻辑通 | 核心事实可能可信，细节存疑 |
| **D** | 低可信度 | 来源不明+逻辑矛盾+动机可疑 | 违背常理、受益者存疑、可能是谣言 |
| **E** | 几乎肯定伪史 | 科学/法律/医学鉴定不通 | 明显违背客观规律、政治宣传 |

### 2.2 分层评估原则

**重要原则**：同一事件的不同层面可信度可能不同。

```
事件: 鸿门宴
  ├─ 核心事实（鸿门宴发生）: A级
  ├─ 基本经过（樊哙闯帐）: B级
  └─ 具体对话细节: C-D级
```

**评估维度**：
- **核心事实**：事件是否发生
- **基本经过**：主要人物行动
- **具体细节**：对话、神态、心理描写

## 三、七大推理方法

本方法论整合传统史源批判与李开元《秦谜》系列的推理方法。

### 方法1：医学/科学鉴定法

**定义**：应用基本医学和科学常识，验证历史记载是否符合客观规律。

**常用知识库**：
- 生理常识：怀孕周期、生育年龄
- 时间常识：距离与速度、工程耗时
- 数量常识：人口容量、军队规模

**应用步骤**：
```
1. 识别可验证的科学要素
2. 调查古代医学知识水平
3. 应用基本科学常识
4. 检验是否存在科学矛盾
5. 判断记载的真实性
```

**案例：秦始皇身世的医学鉴定**

```
《史记》记载:
085_吕不韦列传: "姬自匿有身，至大期时，生子政"

医学分析:
  - "大期"= 十个月（足月怀孕）
  - 如果吕不韦献姬时已孕2月 → 应8月生产（早产）
  - 但嬴政"大期时生"→ 说明是足月生产
  - 从子楚娶姬算起，正好十个月

结论:
  医学证据支持嬴政是子楚之子
  "吕不韦献有孕之姬"的说法存在医学矛盾
```

**可机器化**：可建立科学常识库，中高度可机器化(★★★★☆)

---

### 方法2：法律/制度鉴定法

**定义**：运用古代法律制度知识，检验历史事件是否符合法定程序。

**检验维度**：
1. **法律程序**：是否符合当时法律规定？
2. **违法成本**：违法的后果是什么？
3. **制度约束**：制度能否防止该行为？

**应用步骤**：
```
1. 查明当时的法律制度
2. 对照史料与法律规定
3. 检验是否符合法定程序
4. 判断违法的可能性和代价
5. 推断记载的真实性
```

**案例：秦国继承法鉴定**

| 法律要素 | 秦国制度 | 献有孕之姬的合法性 |
|---------|---------|------------------|
| 血统纯正性 | 极为重要（宗法制度） | ❌ 违背 |
| 继承程序 | "刻玉符"严格登记 | ❌ 无法通过 |
| 违法后果 | 废除继承权、杀身之祸 | ❌ 风险极高 |
| 商人理性 | 吕不韦的投资目的 | ❌ 不符合商业逻辑 |

**结论**：
- 献有孕之姬在法律上不可能成立
- 违背吕不韦的商业理性
- 该说法可信度：D-E级（几乎肯定是谣言）

**可机器化**：可建立法律规则引擎，高度可机器化(★★★★★)

---

### 方法3：动机分析法

**定义**：分析当事人的利益诉求，判断行为是否符合"趋利避害"的人性规律。

**核心原则**：
- 人的行为符合利益最大化
- 寻找"谁是受益者"
- 受益者最可能是行为主体或谣言制造者

**分析框架**：
```
FOR 每个相关人物 P:
  计算行为A对P的利益影响
    - 短期利益
    - 长期利益
    - 风险收益比
  判断: A是否符合P的"趋利避害"？
    IF 不符合 THEN 存疑
    IF 符合 THEN P可能是主体/受益者
```

**案例：吕不韦献姬传说的动机分析**

**假设A：传说为真（嬴政确实是吕不韦之子）**

| 相关人物 | 动机分析 | 符合利益吗？ |
|---------|---------|------------|
| 吕不韦 | 泄露真相 → 自毁前程、杀身之祸 | ❌ 严重违背 |
| 子楚 | 真相曝光 → 颜面尽失、继承权受质疑 | ❌ 严重违背 |
| 嬴政 | 真相传播 → 帝位正统性受损 | ❌ 严重违背 |

**假设B：传说为假（嬴政是子楚之子，但吕不韦传播假消息）**

| 相关人物 | 动机分析 | 符合利益吗？ |
|---------|---------|------------|
| 吕不韦 | 传播假消息 → 巩固地位（"皇帝是我儿子"） | ✅ 符合政治利益 |
| 反秦势力 | 传播谣言 → 质疑秦始皇正统性 | ✅ 符合政治目的 |
| 司马迁 | 记录传闻 → 展示秦朝权力黑幕 | ✅ 符合史家立场 |

**结论**：
- 假设B更符合各方利益
- 吕不韦有动机传播假消息（即使嬴政不是他儿子）
- 反秦势力有动机传播谣言
- 该说法可信度：D级（政治谣言）

**可机器化**：可建立利益关系图谱，中度可机器化(★★★☆☆)

### 方法4：逻辑自洽性检验

**定义**：检验史书记载是否符合内部逻辑一致性，识别前后矛盾、因果断裂等不自洽现象。

**检验维度**：
1. **时间逻辑**：事件时间线是否连贯，无矛盾
2. **因果逻辑**：原因→结果链条是否完整，无断裂
3. **人物行为逻辑**：行为是否符合人物性格/利益/能力
4. **叙事逻辑**：细节是否过于完美/戏剧化/不合理

**分析步骤**：
```
1. 检验时间线连贯性（前后事件是否矛盾）
2. 检验因果链完整性（A→B→C是否成立）
3. 检验人物行为合理性（动机/能力/性格是否匹配）
4. 识别叙事异常点（文学加工痕迹）
5. 判断记载的逻辑自洽程度
```

**与SKILL_07c的区别**：
- **07c反常推理**：关注"违反常识/制度的单条记载"（白起坑杀40万）
- **07e逻辑自洽性**：关注"记载内部的逻辑一致性"（秦始皇身世前后矛盾）

**案例：秦始皇身世的逻辑自洽性检验**

**不自洽之一：赵姬隐瞒怀孕的逻辑矛盾**

```
常规逻辑: 怀孕10个月无法隐瞒
记载: "姬自匿有身"

反常分析:
  可能原因1: 记载有误
  可能原因2: 只隐瞒了最初1-2个月
  可能原因3: 完全虚构

判断: 如果只隐瞒1-2个月，逻辑上可行
```

**不自洽之二：至大期时生的时间矛盾**

```
如果吕不韦献姬时已孕2月:
  正常情况 → 8个月生产（早产）
  记载 → "大期时生"（足月）

反常分析:
  可能原因1: 秦朝官方篡改记录（故意写"大期"）
  可能原因2: 确实是足月，说明是子楚之子

判断: 存在两种对立解释，无法确定
```

**不自洽之三：秦国官方沉默的因果矛盾**

```
常规逻辑: 如果真相是吕不韦之子，秦国官方应该澄清
记载: 秦国官方始终沉默

反常分析:
  可能原因: 根本没有这回事，不值得澄清

判断: 沉默本身可能说明是谣言
```

**可机器化**：需建立逻辑规则库+因果链模型，中度可机器化(★★★☆☆)

### 方法5：沉默证据法

**定义**：应有而未有的记载本身就是证据，分析沉默的原因。

**沉默类型**：
1. **偶然失载**：史料散佚、记录遗漏
2. **刻意隐瞒**：政治忌讳、家族丑闻
3. **本来就不存在**：伪史、谣言

**分析步骤**：
```
1. 识别"应有而未有"的记载
2. 列出应该存在的证据清单
3. 分析沉默的原因:
   - 偶然失载？（时间久远）
   - 刻意隐瞒？（政治原因）
   - 本来就不存在？（伪史）
4. 从沉默推断真实性
```

**案例：秦始皇身世的沉默证据**

**应有的证据清单**：

```
如果"吕不韦献有孕之姬"为真，应该存在:
  ✗ 秦国官方承认或澄清
  ✗ 子楚的反应记载
  ✗ 嬴政的回应
  ✗ 吕不韦被诛时的此项罪名
  ✗ 秦国宗室的质疑记录
```

**沉默分析**：

| 应有证据 | 是否存在 | 沉默原因 |
|---------|---------|---------|
| 秦国官方态度 | ✗ 无记载 | 本来就不存在此事？ |
| 子楚反应 | ✗ 无记载 | 本来就不存在此事？ |
| 嬴政回应 | ✗ 无记载 | 可能不屑回应谣言？ |
| 吕不韦被诛罪名 | ✗ 无此罪 | 说明不是真相 |

**结论**：
- 关键证据全部缺失
- 沉默本身说明可能是谣言
- 该说法可信度：D级

**可机器化**：需要完整性知识图谱，低可机器化(★★☆☆☆)

### 方法6：排除法

**定义**：当嫌疑对象有限时，逐一排除不符合逻辑的选项，剩下的即为最可能的答案。

**操作步骤**：
```
1. 列出所有可能的解释/嫌疑对象
2. 分析每个选项的动机和条件
3. 应用其他方法（医学、法律、动机等）逐一检验
4. 排除不符合逻辑的选项
5. 剩下的即为最可能的答案
```

**案例：秦始皇生父之谜**

**假设列表**：

```
解释A: 嬴政是子楚之子
解释B: 嬴政是吕不韦之子
```

**逐一检验**：

| 检验方法 | 解释A（子楚之子） | 解释B（吕不韦之子） |
|---------|----------------|------------------|
| 医学鉴定 | ✅ "大期时生"符合 | ❌ "大期"矛盾 |
| 法律鉴定 | ✅ 符合继承法 | ❌ 违背继承法 |
| 动机分析 | ✅ 各方符合利益 | ❌ 吕不韦违背利益 |
| 沉默证据 | ✅ 无需额外证据 | ❌ 关键证据缺失 |
| 官方记载 | ✅ "庄襄王子也" | ❌ 秦国从未承认 |

**排除过程**：
- 解释B违背医学、法律、动机、沉默证据
- 解释A符合所有检验

**结论**：
- 排除解释B
- 解释A（子楚之子）最可能
- 但承认不确定性：真相不可知

**可机器化**：可建立决策树模型，中高度可机器化(★★★★☆)

---

### 方法7：临场体验法

**定义**：设身处地想象历史情境，用人性常理判断事件合理性。

**应用维度**：
1. **空间体验**：实地考察遗址，感受距离/地形
2. **时间体验**：计算时间跨度，验证可行性
3. **心理体验**：换位思考，判断人物心理
4. **社会体验**：理解当时社会规范和人情常理

**方法特点**：
- 依赖人类共情能力
- 难以完全机器化
- 需要历史想象力
- 结合考古实地考察

**案例：沙丘之谋的临场体验**

**问题**：扶苏为何不验证诏书真伪？

```
临场体验:
  1. 心理: 扶苏性格（仁孝、谨慎）
  2. 社会: 秦朝君父权威（不敢质疑）
  3. 时间: 赵高可能限定时间（紧迫感）
  4. 空间: 扶苏在边疆，信息不对称

人性判断:
  - 孝道压力: 不敢质疑"父皇诏书"
  - 性格因素: 扶苏过于仁孝
  - 蒙恬已劝阻，但扶苏不听

可能性分析:
  选项1: 扶苏过于孝顺，不敢质疑（较可信）
  选项2: 赵高伪造技术高超（可能）
  选项3: 记载有误，实际被迫自杀（存疑）
```

**结论**：
- 从人性角度，扶苏不验证是可能的
- 但仍存在记载失真的可能
- 需结合其他证据综合判断

**可机器化**：低，依赖人类共情和想象力(★☆☆☆☆)

## 四、综合评估流程

### 4.1 完整分析流程

```
【前置步骤：SKILL_07d史源溯源】
  ↓ [输出：史源类型、传播链、传播层级]

【第一层：客观规律检验】
  ↓
1. 医学/科学鉴定
   - 检查生理常识
   - 验证时间/数量合理性
   - 识别科学矛盾
  ↓
2. 法律/制度鉴定
   - 查明当时法律
   - 检查程序合法性
   - 评估违法成本
  ↓

【第二层：人性逻辑检验】
  ↓
3. 动机分析
   - 识别相关人物
   - 分析利益关系
   - 判断"谁是受益者"
  ↓
4. 逻辑自洽性检验
   - 检验时间线连贯性
   - 检验因果链完整性
   - 检验人物行为合理性
  ↓
5. 沉默证据分析
   - 列出应有证据
   - 分析沉默原因
   - 推断隐藏事实
  ↓
6. 临场体验
   - 换位思考
   - 人性判断
   - 常理验证
  ↓

【第三层：综合判断】
  ↓
7. 排除法
   - 汇总所有证据
   - 逐一排除假象
   - 得出最可能结论
  ↓

【最终输出】
  ↓
8. 可信度评级（A/B/C/D/E）
9. 分层评估（核心事实 vs 细节）
10. 多种解释（承认不确定性）
```

### 4.2 评级决策矩阵

**A级（高度可信）**：
- ✅ 史源：档案文献或亲历者口述
- ✅ 传播链：2层以内
- ✅ 科学/法律检验通过
- ✅ 动机分析合理
- ✅ 无明显矛盾

**B级（较为可信）**：
- ✅ 史源：家传口述
- ✅ 传播链：2-3层
- ✅ 核心事实逻辑自洽
- ⚠️ 细节可能有文学加工

**C级（存疑）**：
- ⚠️ 史源：二手传闻
- ⚠️ 传播链：3-5层
- ⚠️ 部分逻辑通，部分存疑
- ⚠️ 核心事实可能可信，细节存疑

**D级（低可信度）**：
- ❌ 史源：来源不明
- ❌ 逻辑矛盾
- ❌ 动机可疑
- ❌ 可能是谣言或政治宣传

**E级（几乎肯定伪史）**：
- ❌ 医学/科学/法律鉴定明确不通
- ❌ 明显违背客观规律
- ❌ 政治宣传或神话色彩

## 零、什么是质量控制

**质量控制（Quality Control, QC）**是通过自动化脚本在**数据生成/修正的每个环节**进行格式/逻辑/一致性检查，及早发现错误，降低人工审核成本。

### 质量控制 vs 反思

| 维度 | 质量控制（QC） | 反思（Reflection） |
|------|-------------|------------------|
| **检查对象** | 格式、边界、数据完整性、规则违反 | 语义准确性、分类正确性、内容合理性 |
| **执行方式** | 规则脚本自动化（lint/validate） | Agent驱动的智能审查 |
| **时机** | 每次数据变更后立即执行 | 完成初次生成后，迭代修正前 |
| **成本** | 极低（秒级执行，无LLM成本） | 中高（分钟级执行，有LLM成本） |
| **可解释性** | 100%可解释（规则明确） | 部分可解释（依赖LLM推理） |
| **典型输出** | PASS/FAIL + 错误位置 + 修复建议 | JSON修正建议 + 新错误模式 |

**协同关系**：
1. QC先行：每次修正后先跑lint，格式错误必须100%消除才能进反思
2. 反思发现的**可规则化错误模式**沉淀为新的QC规则
3. QC验证反思成果：反思修正应用后再跑lint，确保没有引入新格式错误

## 一、质量控制的五个层次

本项目的质量控制体系分为五个递进层次：

```
L5  跨工序一致性（Cross-Phase Consistency）
     ├─ 实体索引 ↔ 标注文本一致性
     ├─ 事件年代 ↔ 年表数据一致性
     └─ 关系三元组 ↔ 实体存在性验证

L4  业务逻辑验证（Business Logic Validation）
     ├─ 时序合理性（后序事件不应早于前序）
     ├─ 年份区间合理性（生年≤卒年）
     └─ 引用完整性（人物ID必须存在于实体库）

L3  数据完整性（Data Integrity）
     ├─ 必填字段非空
     ├─ 字段值域约束（如年份范围 -3000~2000）
     └─ 枚举值合法性（如事件类型必须在11种之内）

L2  语法正确性（Syntax Correctness）
     ├─ 标注边界完整（〖〗成对闭合）
     ├─ JSON/Markdown格式合法
     └─ 正则表达式匹配（如段落编号格式）

L1  文本完整性（Text Integrity）
     ├─ 编码正确性（UTF-8无乱码）
     ├─ 原文不变性（去标记后与原文逐字相同）
     └─ 文件存在性（必需文件齐全）
```

### 检查优先级原则

从L1到L5**逐层执行**，低层级未通过时不执行高层级检查（避免噪音）：

```bash
# 正确的执行顺序
python lint_text_integrity.py      # L1: 文本完整性
&& python lint_markdown.py          # L2: 语法正确性
&& python validate_data_schema.py   # L3: 数据完整性
&& python validate_logic.py         # L4: 业务逻辑
&& python cross_validate.py         # L5: 跨工序一致性
```

## 二、质量控制工具的设计模式

### 2.1 Lint工具设计规范

所有lint工具遵循以下约定：

**命名规范**：
- `lint_*.py` — 检查单一工序内的格式/语法错误
- `validate_*.py` — 检查数据完整性和业务逻辑
- `cross_validate_*.py` — 检查跨工序一致性

**输入输出约定**：

```python
# 输入：文件路径或目录
python lint_markdown.py chapter_md/001_*.md     # 单文件
python lint_markdown.py chapter_md/             # 整个目录
python lint_markdown.py --all                   # 全部数据

# 输出格式：
# ✅ PASS（无错误） → 返回码0
# ❌ FAIL（有错误） → 返回码1，输出错误详情
```

**输出格式标准**：

```
文件：chapter_md/001_五帝本纪.tagged.md

❌ 错误 [L2-边界完整性]
  第42行：未闭合的人名标注
  位置：黄帝者，少典之子〖@姓公孙
  建议：补全闭合符号 → 〖@姓公孙〗

⚠️  警告 [L3-数据完整性]
  第67行：空地名标注
  内容：〖=〗
  建议：删除空标注或补全内容

ℹ️  信息 [统计]
  总实体标注：1,234
  错误数：2
  警告数：1

---
❌ 检查失败：发现2处错误，1处警告
```

**错误分级**：

| 级别 | 符号 | 说明 | 阻断发布？ |
|------|-----|------|----------|
| **ERROR** | ❌ | 必须修复，否则数据不可用 | 是 |
| **WARNING** | ⚠️ | 应该修复，但不影响基本功能 | 否 |
| **INFO** | ℹ️ | 信息性提示，无需修复 | 否 |

### 2.2 核心Lint工具实例

#### 实例1：`lint_markdown.py` — 标注文本格式检查

**检查项（L1-L2）**：

1. **文本完整性（L1）**
   - 文件编码为UTF-8
   - 去标记后与原文`chapter_numbered/*.txt`逐字相同

2. **标注边界完整性（L2）**
   ```python
   # 检查〖〗成对
   open_count = text.count('〖◆)
   close_count = text.count('〗')
   if open_count != close_count:
       error(f"〖{open_count}个 ≠ 〗{close_count}个")

   # 检查嵌套（不允许〖〖@X〗〗）
   if re.search(r'〖[^〗]*〖◆, text):
       error("发现嵌套标注")

   # 检查边界损坏（标注不应包含标点）
   if re.search(r'〖@[^〗]*[，。、；：]', text):
       error("人名标注包含标点")
   ```

3. **空标注检查（L2）**
   ```python
   if re.search(r'〖[@=;#%&\'^~\*!\+\$]\s*〗', text):
       warning("发现空标注")
   ```

4. **段落编号连续性（L2）**
   ```python
   # [1], [1.1], [1.2], [2], [2.1] ...
   # 检查层级跳跃（不允许 [1] → [1.2]）
   # 检查编号回退（不允许 [2.3] → [2.1]）
   ```

**使用**：
```bash
# 检查单章
python lint_markdown.py chapter_md/001_五帝本纪.tagged.md

# 检查全部（CI/CD集成）
python lint_markdown.py --all --exit-on-error
```

#### 实例2：`lint_ce_years.py` — 事件年代逻辑检查

**检查项（L3-L4）**：

1. **数据完整性（L3）**
   ```python
   # 检查年份格式
   valid_patterns = [
       r'\(公元前\d+年\)',              # 确定纪年
       r'\[约公元前\d+年\]',            # 不确定纪年
       r'\[约公元前\d+—前\d+年\]',      # 区间纪年
   ]
   if not any(re.match(p, time_field) for p in valid_patterns):
       error(f"年份格式不合法: {time_field}")

   # 检查年份范围合理性
   if ce_year < -3000 or ce_year > 100:
       warning(f"年份超出史记范围: {ce_year}")
   ```

2. **时序合理性（L4）**
   ```python
   # 同章节内事件应按时间递增
   for i in range(1, len(events)):
       if events[i].ce_year < events[i-1].ce_year:
           diff = events[i-1].ce_year - events[i].ce_year
           if diff > 3:  # 允许3年容差
               error(f"时序倒退: {events[i-1].name}({events[i-1].ce_year}) → {events[i].name}({events[i].ce_year})")
   ```

3. **年份跳跃检测（L4）**
   ```python
   # 相邻事件年份差距>100年，可能有错
   for i in range(1, len(events)):
       diff = abs(events[i].ce_year - events[i-1].ce_year)
       if diff > 100:
           warning(f"年份跳跃: {events[i-1].name}({events[i-1].ce_year}) → {events[i].name}({events[i].ce_year}), 差距{diff}年")
   ```

4. **已知年份交叉验证（L4）**
   ```python

#### 实例3：`validate_tagging.py` — 原文不变性验证

**核心检查（L1）**：

```python
def remove_all_tags(text):
    """去除所有标注符号，还原纯文本"""
    # 去除18类实体标注
    text = re.sub(r'〖[@=;#%&\'^~\*!\+\$]([^〖〗|]+?)(?:\|[^〖〗]*)?〗', r'\1', text)
    # 去除段落编号
    text = re.sub(r'^\[\d+(?:\.\d+)*\]\s*', '', text, flags=re.MULTILINE)
    # 去除Markdown标题/引用/分割线
    text = re.sub(r'^#{2,4}\s+.*$', '', text, flags=re.MULTILINE)
    text = re.sub(r'^>\s*', '', text, flags=re.MULTILINE)
    text = re.sub(r'^---+\s*$', '', text, flags=re.MULTILINE)
    return text.strip()

def validate_chapter(md_path, txt_path):
    """验证标注后文本与原文逐字相同"""
    original = Path(txt_path).read_text('utf-8')
    tagged = Path(md_path).read_text('utf-8')

    stripped = remove_all_tags(tagged)
    clean_original = remove_all_tags(original)

    # 标准化后逐字比对
    norm_stripped = re.sub(r'\s+', '', stripped)
    norm_original = re.sub(r'\s+', '', clean_original)

    if norm_stripped != norm_original:
        # 找出首个差异位置
        for i, (c1, c2) in enumerate(zip(norm_stripped, norm_original)):
            if c1 != c2:
                context_start = max(0, i-20)
                context_end = min(len(norm_stripped), i+20)
                error(f"第{i}字符不同:\n"
                      f"  标注文本: ...{norm_stripped[context_start:context_end]}...\n"
                      f"  原文: ...{norm_original[context_start:context_end]}...")
                return False

        # 长度不同
        error(f"长度不同: 标注{len(norm_stripped)}字 ≠ 原文{len(norm_original)}字")
        return False

    return True
```

## 三、跨工序一致性检查（L5）

### 3.1 实体索引一致性

**检查目标**：
- 标注文本中的实体在实体索引中必须存在
- 实体索引中的出处必须能在标注文本中找到

```python
def cross_validate_entities():
    """实体索引 ↔ 标注文本双向验证"""
    # 从标注文本提取所有〖@人名〗
    tagged_persons = set()
    for md_file in CHAPTER_DIR.glob("*.tagged.md"):
        text = md_file.read_text()
        for match in re.finditer(r'〖@([^〖〗|]+)(?:\|([^〖〗]+))?〗', text):
            display_name = match.group(1)
            canonical_name = match.group(2) or display_name
            tagged_persons.add(canonical_name)

    # 从实体索引加载所有人名
    entity_index = json.loads(Path("kg/entity_index.json").read_text())
    indexed_persons = set(entity_index.get("persons", {}).keys())

    # 检查：标注中出现但索引中不存在
    missing_in_index = tagged_persons - indexed_persons
    if missing_in_index:
        warning(f"以下{len(missing_in_index)}个人名在标注文本中出现但实体索引中缺失:\n"
                f"  {', '.join(list(missing_in_index)[:10])}")

    # 检查：索引中存在但标注中未出现（可能是消歧规范名）
    missing_in_text = indexed_persons - tagged_persons
    if len(missing_in_text) > len(indexed_persons) * 0.1:
        warning(f"实体索引中有{len(missing_in_text)}个人名在标注文本中未找到，"
                f"占比{len(missing_in_text)/len(indexed_persons):.1%}，可能存在问题")
```

### 3.2 事件年代一致性

**检查目标**：事件年代标注应与年表数据一致

```python
def cross_validate_dates():
    """事件年代 ↔ 年表数据交叉验证"""
    # 加载年表数据
    reign_periods = json.loads(Path("kg/chronology/data/reign_periods.json").read_text())

    # 加载所有事件
    for event_file in EVENTS_DIR.glob("*_事件索引.md"):
        events = parse_events(event_file)

        for event in events:
            # 提取纪年标记（如"秦昭王十三年"）
            reign_match = re.search(r'〖&([^〗]+)〗〖%([^〗]+)〗', event.time_raw)
            if not reign_match:
                continue

            ruler = reign_match.group(1)
            year_in_reign = parse_year(reign_match.group(2))

            # 从年表查询公元年
            if ruler in reign_periods:
                reign_start = reign_periods[ruler]["start"]
                expected_ce = reign_start + year_in_reign - 1

                # 与事件标注的公元年对比
                if abs(event.ce_year - expected_ce) > 1:
                    error(f"{event.name}: 标注{event.ce_year}年 ≠ 年表推算{expected_ce}年 "
                          f"({ruler}{year_in_reign}年)")
```

def validate_relation_integrity():
    """关系三元组 → 实体存在性验证"""
    entity_index = json.loads(Path("kg/entity_index.json").read_text())

        if "evidence_chapter" in rel:
            evidence_file = CHAPTER_DIR / f"{rel['evidence_chapter']}_*.tagged.md"

### 5.2 常见陷阱

1. **过度检查** — 不要检查"可能"的问题，只检查"确定"的错误
   - ❌ "这个人名看起来不太对" → 太主观，留给反思
   - ✅ "人名标注包含标点符号" → 明确违反格式规则

2. **检查不独立** — 每个工具应能独立运行，不依赖其他工具的输出
   - ❌ `lint_B.py`依赖`lint_A.py`生成的中间文件
   - ✅ `lint_B.py`直接读取源数据文件

3. **输出不友好** — 错误信息应指明位置+原因+建议修复
   - ❌ "检查失败"
   - ✅ "第42行：未闭合的人名标注，建议补全〗符号"

4. **没有容差** — 业务逻辑检查应允许合理误差
   - ❌ 年份相差1年就报错（古代纪年本身有歧义）
   - ✅ 年份相差>3年才报错

5. **忽略边界情况** — 处理空文件、空数据、极端值
   - 空文件怎么办？（应报warning而非crash）
   - 数据为空数组怎么办？（应报info "无数据"）
   - 年份为0怎么办？（公元1年前后没有公元0年）

## 六、质量控制的最佳实践

### 6.1 设计原则

1. **快速失败（Fail Fast）** — 低层级错误立即阻断，不执行高层级检查
2. **清晰反馈（Clear Feedback）** — 错误信息包含：位置+原因+建议修复
3. **分级输出（Tiered Output）** — ERROR必须修复，WARNING建议修复，INFO仅提示
4. **批量模式（Batch Mode）** — 支持`--all`参数批量检查所有文件
5. **CI/CD友好（CI/CD Friendly）** — 返回正确的exit code（0=PASS, 1=FAIL）

## 八、总结

质量控制是知识库建设的**安全网**。通过五层质检体系，我们将错误拦截在不同阶段：

- **L1-L2（格式层）**：拦截80%的低级错误（边界损坏、语法错误）
- **L3-L4（逻辑层）**：拦截15%的中级错误（时序倒退、值域越界）
- **L5（一致性层）**：拦截5%的高级错误（跨工序不一致）

**核心洞察**：
1. **质量控制≠反思** — QC是规则驱动的快速检查，反思是语义驱动的智能审查
2. **自动化优先** — 能用规则检测的就不要用LLM，降低成本提升效率
3. **分层递进** — 低层级通过才执行高层级，避免噪音干扰
4. **持续监控** — 质量指标应纳入CI/CD，每次变更都触发检查
````
