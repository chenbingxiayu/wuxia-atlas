## 二、核心设计决策：为什么用〖〗Token 而不用 XML/HTML 标签

本项目的语义标注采用轻量 CJK 符号（`〖@人物〗`、`〖=地点〗`、`〖☆武功技艺〗`、`⟦⊞战斗交锋⟧` 等），而非 XML（`<person>人物</person>`）或 HTML（`<span class="person">人物</span>`）。这是**可读性**与**语义精确性**之间的刻意权衡，论证整体承自史记版，示例武侠化。

### 2.1 方案对比

```text
底本原文：玉罗刹一剑挥出，恰似白虹贯日。

XML 标注：
<person>玉罗刹</person>一剑挥出，恰似<martial-art>白虹贯日</martial-art>。

HTML 标注：
<span class="person">玉罗刹</span>一剑挥出，恰似<span class="martial-art">白虹贯日</span>。

Token 标注：
〖@玉罗刹〗一剑挥出，恰似〖☆白虹贯日〗。
```

### 2.2 七维选型对照表（照搬史记版）

| 维度           | XML/HTML                              | 〖〗Token                                       |
| -------------- | ------------------------------------- | ----------------------------------------------- |
| **人眼可读性** | 标签淹没原文，标注后几乎无法直接阅读  | 标记轻量，标注后仍可流畅阅读原文                |
| **标注效率**   | 打开/关闭标签冗长，LLM 输出 Token 消耗大 | 单字符类型标记，LLM 输出紧凑                 |
| **git diff**   | 标签噪音严重，差异难以 review          | diff 清晰，改动一目了然                          |
| **嵌套处理**   | 允许任意嵌套，但解析复杂              | 拍平策略：外层保留、内层不复制（`fix_nested_annotations.py` 清理） |
| **语义精确性** | 可附加任意属性（id/type/ref 等）       | 仅类型标记，属性通过外挂 JSON 补全               |
| **编辑门槛**   | 需要了解 XML 语法，标签易写错          | 选中文本加前后缀即可，直觉操作                  |
| **渲染无关性** | HTML 标注与渲染耦合                    | 同一份标注可渲染为 HTML/PDF/LaTeX/JSON           |

> 历史注记（史记 v1.0→v2.0）：`$官职$` 曾与 Markdown math 语法冲突，v2.0 换符号解决。武侠库符号体系由 `symbols.py` 唯一定版并经 `lint_symbol_conflicts.py` 冲突扫描，此坑不再存在，仅作决策背景保留。

### 2.3 关键洞察（三条，武侠化）

1. **白话章回标注的首要矛盾同样是可读性**。34 部书 × 1,378 回 × 约 1,700 万字的标注文件，标注员与 agent 需要频繁阅读和修改。XML 标注后原文几乎不可读（标签字符数常超过原文字符数），在逐回人工抽检的作业模式下不可接受。

2. **语义精确性通过分层补全**。Token 标记只承载"类型"这一维信息，更丰富的语义（消歧、别名、跨书身份）通过外挂 JSON 元数据层在渲染时注入，而非塞进标记本身：

   ```text
   源文件：〖@玉罗刹〗                        ← 只标类型
   消歧层：{"baimofanzhuan": {"玉罗刹": "练霓裳"}}   ← JSON 补全书内消歧
   别名层：{"练霓裳": ["玉罗刹", "白发魔女"]}        ← JSON 补全别名
   跨书层：series_identities 归并表（D07）            ← 跨书 canonical，只留接口
   渲染时：<a href="person.html#练霓裳"><span class="person" title="即练霓裳">玉罗刹</span></a>
   ```

3. **史记 v1→v2 的教训验证了这一选择**。史记项目初期曾用 HTML `<span style="color:...">` 标注，标注后原文完全不可读，被迫批量回退为 Token 标记。武侠库**直接从 Token 起步**，不重演这段返工。

### 2.4 与 TEI/XML 标准的关系

学术数字人文项目（如 TEI P5）通常采用 XML 标注。本项目的选择并非否定 TEI，而是针对 **AI Agent 驱动的大规模标注**场景做的工程权衡：

- TEI 适合：小规模、高精度、学术发表、需要复杂属性和关系；
- Token 适合：大规模（约 1,700 万字）、AI 批量标注、频繁迭代、需要人眼审核；
- 两者可桥接：Token 标注 + JSON 元数据 → 可导出为 TEI XML（导出脚本**未建**，见附录 B）。

## 四、结构层三硬接口（引 02ab §1.1）

结构层不是孤立的排版工序，两处硬接口决定其定版权限，第三处决定其定位符体系：

1. **对 01g（实体层）**：块类型/文本模式两个枚举由 02ab 定版；01g 的"围栏内不标注"由 02ab §4.4 细化为分层豁免（词/诗/歌/对联/回末对实指可标、回末全不标、书信事件不核实、口诀技术名可标）；
2. **对 04f（动词/事件层）**："韵文提及不计入正文事件密度"依赖 02ab §5 韵文判定；"回末套语/回目预告不抽事件"依赖 02ab §6 套语分级（01g 负规则十三）；
3. **对 D07 跨书治理**：跨书定位锚点 `{作品ID}#pn-r{回号}.{段}` 由 02ab §3.5 定版（`ANCHOR_FMT`，`symbols.py` 承接）；回号层保证 1,378 回无歧义。

## 结语

武侠结构层继承了史记版最重要的一个判断：**标注格式是人读的，不是机器独享的**。Token 符号让 1,700 万字在标注后仍可通读，让 diff 干净可审，让剥标还原（S-01a 铁律）有兑现的基础。本文是索引：符号找 01g，骨架找 02ab，关系找 02d，数字找 02f，修辞找 02j/02k——各专项冲突时，以已定版上游为准。
