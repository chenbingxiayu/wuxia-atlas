## 一、技能定位

### 1.1 词表 = 数据，不是代码

- 词表条目是**数据**：有 schema、有版本、有来源、有证据；词条的增删改走数据流程（§七），不走改代码流程。
- 词表正则、lint 规则是**代码**：它们消费词表数据而生成，自身不承载词条。同一份词表可同时喂给提示词召回、lint 兜底、搜索联想——靠的是统一 schema 与版本声明（§4.4），不是各自硬编码。
- 因此本篇只定**格式合同与运营规则**，不写实现代码；"一词表一文件、源表唯一编辑面、派生单向再生成"（§四）就是数据与代码的分界线。

**理由**：前人实验结论四证实，职衔 1→53、时间 16→6 的修复全部靠词表正则兜底——若词条散落在提示词与脚本里，每修一个盲区都要改代码、改提示词、重发布；数据化之后改一行词表、重跑派生即可。

## 三、统一 Schema（Q2，本任务核心）

### 3.1 设计原则

1. **最小骨架**：所有表共享 8 个骨架字段；凡两表以上需要的字段进共享扩展池，表私有字段进登记制。
2. **旧数据无损**：五种变体的每个旧字段在骨架或扩展池中有唯一去向（§3.6）；迁移只改名、并列表、派生补全，不改语义、不删数据。
3. **档位全局统一**：tier（三档）语义以 04f 定版为准，conf 图例以招式表定版为准，全库一张表一套档位字典（§3.7 枚举）。
4. **模板与实词同构**：词族模板与字面词形共用 surface 字段，用 surface_kind 区分（§3.4）。

### 3.2 通用骨架（八字段）

> **对合同基线的显式声明**：合同 Q2 列举的通用骨架为七字段（surface/type 或 domain/tier/conf/evidence/status/version）；本稿在其上**新增 canonical 为第 8 个骨架字段**——canonical 是变体一/五的既有字段、消歧映射类表（WL-01 等 P0 表）的主键，缺省=surface 的自指规则让动词/套语类零成本兼容。这是有理由的显式扩展，非静默矛盾（v2 把 canonical 降级为各表扩展字段，消歧表失去一等公民主键，否决）。

| # | 字段 | 类型 | 必填 | 语义与规则 | 示例 |
|---|---|---|---|---|---|
| 1 | surface | string | 必填 | 词形；字面串或受控模板（§3.4）。模板条目须同时给 surface_kind | `"一羽千钧"` / `"欲[知/如]后事如何*[请听/且听]下回分解"` |
| 2 | canonical | string | 条件必填 | 规范形式（稳定键）。**缺省 = surface（自指）**；凡消歧/映射类表必填 | `"练霓裳"`（surface=白发魔女 时） |
| 3 | type 或 domain | string | 必填（二选一） | 实体表用 type（01g 15 类实体码）；非实体表用 domain（动词域 ⊞、套语、语式、停用、称谓等域码）。同一词表内只用其一 | `"绰号"` / `"⊞"` / `"招式"` |
| 4 | tier | enum | 必填 | 全局运营档位：`auto`（高置信自动补标）/`review`（多义待审）/`watch`（观察）。语义以 04f 定版为准 | `"review"` |
| 5 | conf | enum | 必填 | 证据强度：`strong`（明文直证）/`ok`（窗口共现/多源间接）/`weak`（先验/孤证，不发布）。图例继承招式表 conf_legend | `"ok"` |
| 6 | evidence | array | 条件必填 | 证据锚：`[{book, loc, kind}]`，loc 格式 `回:段`（允许 `回末`/`回首` 位置词）。吸收 01g refs、moves/verbs evidence | `[{"book":"江湖三女侠","loc":"25:65","kind":"共现招式"}]` |
| 7 | status | enum | 必填 | 条目生命周期：`auto`（机核通过）/`待审`（人工队列）/`已核准`。流转规则 §3.3 | `"已核准"` |
| 8 | version | int | 必填 | 条目修订号：入库=1，每次修订 +1。文件级版本在 meta（§3.7） | `1` |

**canonical 缺省自指的理由**：04f 动词、套语模板多数没有独立规范形，强制必填会逼出大量冗余；"缺省=surface"使四列骨架（01g/02h）无损落位，又让 verbs 类表零成本兼容。

### 3.3 tier × conf × status 关系裁决

三个字段各管一件事，不得互相劫持（v2 的"conf 从 tier 派生"使两轴合并为一个开关，已否决——W13）：

- **conf 管证据**：这条词形的证据有多硬（静态属性，随考订更新）。
- **tier 管运营**：这条词形在管线里被允许做什么（动态档位，随验证流转）。
- **status 管流程**：这条数据处于生命周期的哪一步（auto=机核通过；待审=挂人工队列；已核准=人工确认）。

**初始 tier 派生规则（迁移与新增通用，方向唯一：conf×status→tier）**：

| conf＼status | auto（机核通过） | 待审 | 已核准 |
|---|---|---|---|
| strong | **auto** | review | auto |
| ok | review | review | auto |
| weak | **watch**（恒定） | watch | watch* |

\* 核准 weak 条目前必须先补证据把 conf 升到 ok/strong；"人工核准一个无锚条目"是被禁止的操作（§九 W02）。

**发布规则**（继承招式表图例"weak 先验不发布"）：

- R1 `conf=weak` ⇒ `tier=watch` ⇒ 只进 `<wl>_watch.json`，永不进发布视图。
- R2 `verify=unverified` 的条目禁入任何视图（必须先修正或删除，02h 铁律继承）。
- R3 `tier=auto` 的额外前置见 §4.3（计数验证/剥标还原），本表只给派生初值。

**示例**：招式"一羽千钧"（conf=ok, status=auto）迁移后 tier=review；04f"点穴"（tier=auto, status=auto, evidence kind=标注）迁移补 conf=strong，派生校验 tier=auto 与原值一致。

### 3.4 surface 词形与受控模板语法

- **literal**（缺省）：字面串，规范化（繁简/全半角/异体归并）后精确匹配。例：`铁掌`、`白发魔女`。
- **template**（surface_kind=template）：受控模板，仅三种算子：

| 算子 | 含义 | 示例 |
|---|---|---|
| `[a/b]` | 枚举选一 | `欲[知/如]后事如何*[请听/且听]下回分解` |
| `*` | 任意填充（含空），仅用于召回候选 | `天山*剑法`（候选发现用） |
| `{槽名}` | 具名槽位，取值域指向其他词表 | `人称{绰号}`（槽位→WL-01） |

- **模板命中 ≠ 实词**（§九 W03）：模板条目用于候选召回与 lint 拦截；只有当槽位被某词表实体填充后，填充结果才可作为标注候选。例：WL-11 语式 `人称{绰号}` 命中"人称玉罗刹"时，产出候选 surface=玉罗刹，而非把整个语式当实体标注。
- **拦截语义与证据档位脱钩**：模板命中与否是 surface_kind/信号职责（signal_role）层面的事；命中所得文本的证据强度仍按 §6.1 五分类判定（绰号截称命中是 partial，可召回）——不得因"来自模板"就压档（v2 把 partial 一律排除出实体识别，混淆了两个层面，已否决）。
- **理由**：02ab 套语词族与 #7 检测语式都是模式而非词形，若不让 surface 承载模板，就得为它们另立格式，碎片化重现；三种算子刚好覆盖既有两类资产的表达需求，不引入正则全集（防误写、防灾难回溯；扩容议题见附录 B-2）。

### 3.5 扩展字段规范

> **格式定版（对 v2 分歧的裁决）**：扩展字段**扁平放在条目顶层**、snake_case 命名、经共享池或 meta.extensions 登记后使用。**不引入 `ext` 包裹对象**——moves-v1/verbs-v1 实测字段（parent_art/sect/used_by/complements 等）均为顶层 snake_case，嵌套包裹与小驼峰都会给 222 条已上线数据制造迁移 churn；也**不双轨兼容**（"ext 推荐、顶层历史兼容"两可制 = 同一数据两种形态，必漂移）。

**共享扩展池**（≥2 表复用，登记于此；未登记字段不得出现在派生 JSON 中）：

| 字段 | 类型 | 使用表 | 语义 | 示例 |
|---|---|---|---|---|
| surface_kind | enum | WL-10/11/凡模板 | literal \| template | `"template"` |
| disambig | string | WL-01/08/09 | 同名限定词（书域/身份域） | `"甲书"` |
| book_scope | array | 全部 | 适用书目（`["全库"]` 或书目列表） | `["白发魔女传","七剑下天山"]` |
| verify | enum | 全部 | 验证五分类（武侠化语义 §六） | `"verbatim"` |
| subtype | string | WL-05 | 动词子类（04f 原字段） | `"擒控"` |
| senses | array | WL-05 | 义项模式（04f 原字段） | `[{"pattern":"战斗语境+人身对象","domain":"⊞"}]` |
| complements | array | WL-05 | 常接补语（04f 原字段） | `["倒","住"]` |
| collocations | array | WL-05 | 搭配（04f 原字段） | `[{"type":"^","strength":"strong","predicate":"点穴"}]` |
| parent_art | string | WL-06 | 所属功法，外键→WL-07 | `"无极剑法"` |
| sect | string | WL-06/07 | 门派，外键→WL-08 | `"无极派"` |
| used_by | array | WL-06/09 | 使用者计数（moves 原字段） | `[{"name":"冯琳","n":7}]` |
| struct_meaning | string | WL-10/11 | 结构含义（02ab 原字段） | `"回末套语"` |
| confirm_signal | string | WL-10/11 | 第二确认信号（02ab 原字段） | `"回末位置"` |
| freq | string | WL-10/11 | 实测频级，原样保留（02ab 原字段） | `"27/32回"` |
| signal_role | enum | WL-04/10/11 | positive（正向召回）\| decoy（伪，拦截）\| monitor（缺位监视） | `"positive"` |
| notes | string | 全部 | 备注（异体、争议、来源引用） | `"外部职官表注释，非语料锚"` |

**命名规则**：

- E1 小写下划线（snake_case）；禁止与骨架 8 字段重名；**禁用中文键与驼峰键**（与 moves-v1/verbs-v1 实测字段名保持同形）。
- E2 禁止语义劫持骨架字段（如给 status 另立枚举——§九 W06）。
- E3 复用于 ≥2 表的字段必须登记进共享扩展池；表私有字段直接语义命名，并在该表 meta.extensions 里自描述登记。
- E4 外键字段在 meta.extensions 登记目标表：`{"field":"parent_art","ref":"WL-07"}`；值暂存字符串，外键校验由派生脚本按登记执行。

**示例**：moves-v1 的 parent_art/sect/used_by 是表私有字段转共享池的实例——WL-07/08 落地后它们立即被三张表复用，故入池。

### 3.7 外置 JSON 格式定版

**文件组织**：一词表一组三件 + 一张注册表。

```
wordlists/
├── _registry.json          # 词表注册表（§二总表的机读版，派生自本文档）
├── moves_source.md         # 人工源（唯一编辑面）
├── moves.json              # 发布视图（tier∈{auto,review} 且 conf≠weak 且 verify≠unverified）
├── moves_watch.json        # 观察视图（watch / conf=weak / 先验）
├── verbs_source.md / verbs.json / verbs_watch.json
└── ……（每张词表同名三件）
```

**meta 块规范**（对齐招式表 meta 风格）：

| 键 | 值 | 说明 |
|---|---|---|
| schema | `wuxia-wordlist/1.0` | 统一 schema 版本（全库唯一 schema 命名；文件内不再出现"wordlist-wuxia-v1"式第二命名） |
| wordlist | 表码（如 `moves`） | 与 _registry.json 对应 |
| version | `vMAJOR.MINOR` | MAJOR=字段/枚举变更；MINOR=条目增删改（§4.4 批次绑定用）。条目级 version 为修订号 int，两版分层 |
| generated | ISO 时间戳 | 派生时间 |
| based_on | 来源说明 | 继承招式表（如"moves-v1 222 条迁移 + 章回版扫描 v3"） |
| totals | `{all, by_tier, by_conf}` | 与源表行数对账（§十 发布前检查） |
| conf_legend | `{"strong":"明文","ok":"窗口共现","weak":"先验不发布"}` | 招式表图例原文继承，全库统一 |
| tier_legend | `{"auto":"高置信自动补标","review":"多义待审","watch":"观察"}` | 04f 档位语义继承，全库统一 |
| extensions | 自描述数组 | `{"field":"parent_art","ref":"WL-07"}` 等（§3.5-E4） |

| 字段 | 枚举值 | 出处 |
|---|---|---|
| tier | auto / review / watch | 04f 定版语义，本文全局化 |

| evidence.kind | 明文 / 标注 / 共现（含"共现招式"等原值）/ 回末套语 / 别名共现 / 考订 / 先验 | 登记制：迁移保留原值，新 kind 须先登记 |

## 四、双轨与三档运营（Q3）

### 4.1 双轨铁律（02h 铁律继承）

- **T1 源表唯一编辑面**：一切词条增删改只发生在 `wordlists/<wl>_source.md`（Markdown 表格，人工可读可 diff）。
- **T2 派生单向再生成**：`<wl>.json` 与 `<wl>_watch.json` 只由派生流程从源表生成；手改派生 JSON 无效且会在下次再生成时被冲掉（§九 W01）。
- **T3 候选不直写**：扫描管线发现的新候选只写入源表的「候选区」（折叠节，带扫描批次号），经门槛确认后才转为正式条目；候选永不直接进派生 JSON。
- **T4 视图分离**：发布视图与观察视图物理分文件；watch 条目晋升后经再生成自然进入发布视图，降级同理——**视图内容永远服从源表，互不冲掉**。
- **T5 一致性自动校验**：派生流程接入 CI——源表与派生 JSON 的 totals/版本不一致即报警阻断合并（收 v2 W4 之长）；派生对账 diff 与 git 历史审查是 W01 的常态化检出手段。

**理由**：人工考订（慢、准）与语料扫描（快、广）节奏不同；双轨让扫描管线随时重跑而不踩人工成果，也让人工修订随时发布而不等管线。

### 4.2 源表更新流程

1. 在 `<wl>_source.md` 修改/新增条目（含骨架 8 字段与登记扩展）。
2. 跑该表派生（源表 → 发布/观察两视图），派生对账：totals 与源表行数一致、watch 未混入发布（CI 校验，T5）。
3. meta.version 递增（条目增删改升 MINOR；字段/枚举变更升 MAJOR 并同步本文档 §3.7 字典）。
4. `_registry.json` 再生成（登记该表最新版本号）。
5. 消费方按 §4.4 声明新版本；旧版本 tagged 语料不强制重标。
6. 回滚 = 源表 git revert + 重跑派生（派生无状态，随时可重建）。

### 4.3 三档运营（04f 定版语义的全局泛化）

| 档位 | 准入条件 | 运营动作 | 晋升 | 降级/退出 |
|---|---|---|---|---|
| **auto**（高置信自动补标） | conf=strong 且 status=已核准；或 status=auto 且通过两个机核前置：**计数验证**（词表正则在人工抽样集上的命中数与预期标注数完全一致）与**剥标还原**（对已标注章回剥掉该表覆盖类的标注→仅用词表正则重标→还原率 ≥95%，对齐 02h 定位率目标） | 直接进入 LLM 提示词的词表正则兜底层 | ——（已是顶档） | lint 报误标 → 立即降 review，加语境限定 |
| **review**（多义待审） | conf=ok；或 conf=strong 但未过机核前置；或 watch 晋升 | 逐条语境判定：每条写出适用语境条件（如"仅战斗语境+人身对象"），人工核准后 status=已核准；争议条目双人复核 | 连续两批剥标还原 ≥95% 且抽样 20 条零误标 → auto | 发现歧义/同名冲突 → 降 watch 并补 disambig |
| **watch**（观察） | conf=weak；或 verify∈{narrative, 先验无锚}；或负清单例外条目（§5.4） | 观察回填：每轮语料重扫描统计命中；命中即登记 evidence | 命中 ≥3 **独立案例**（不同回目或不同书目；同回/同段重复不算）→ 升 review | 连续两轮零命中且无考订佐证 → 移入源表归档节（不删，保留轨迹） |

**示例**：

- auto：04f"点穴"——evidence 明文标注、计数验证与剥标还原通过 → 自动补标层直接使用。
- review：招式"一羽千钧"（conf=ok）——逐回核对其窗口共现是否真实用招，核准后升 auto。
- watch：职衔候选"铁掌(甲书)"——先验疑为书域限定词，重扫描在第 3 书命中 3 处独立案例 → 升 review 并固化 disambig=甲书。

### 4.4 消费协议（词表版本与标注批次绑定）

- P1 **批次声明**：每次 LLM 标注批次启动时，声明所用词表快照（各表 meta.version 的集合，记入批次清单），如 `wordlists: moves@v1.4, verbs@v2.0, guanzhi@v0.3`。
- P2 **语料留痕**：标注产物的 meta 回写 `wordlists_version` 字段，tagged 语料与词表版本一一对应（边界案例八的落点）。
- P3 **lint 校验**：lint 启动时比对语料 meta 与当前 `_registry.json`；版本不一致 → WARN（提示复核，不阻断——旧批次语料允许存在）。版本变更**不强制重开批次**（v2"版本变更必须重新生成批次"作废：MINOR 升版全量重标不可执行，版本留痕已保证可复现）。
- P4 **同批同版**：同批次内禁止混用版本；中途升版必须重开批次。
- P5 **MAJOR 升版**：字段/枚举变更后，旧版本语料不强制重标，但渲染层需能显示"该标注产生于 v1.x"。

**逐消费方接口**（读什么、按什么过滤、版本要求）：

| 消费方 | 读取与过滤 | 版本要求 |
|---|---|---|
| A LLM 标注提示词 | 发布视图 entries；按 tier（兜底层只用 auto）+type/domain 过滤 | 必须指定版本（批次声明 P1） |
| B lint 家族 | 发布+观察视图；按 signal_role 区向（decoy 拦截）+type 过滤 | 必须指定版本 |
| C 全站搜索 | 发布视图；按 surface/canonical 索引（含 aliases） | 取最新（低风险展示） |
| D 分类树五件套 | 叶子表引用键；消费主表 tier/conf 展示 | 随主表 |
| E 阅读器/渲染 | 发布视图；按 surface 匹配专名候选 | 取最新 |
| F 考订工具 | 全条目（含观察视图）；按 conf/status 过滤 | 必须指定版本 |

**理由**：规范矛盾提示词解决不了（前人结论三）——唯一能让"词表正则兜底"可复现、可审计的，就是把"数据版本"当作标注结果的一部分，如同编译器版本之于产物。

### 5.4 入库门槛（07c"3+ 案例才保留"精神的前置引用）

- **一般规则**：正式条目须有 ≥3 个独立案例（不同回目或不同书目），且至少 1 条带 evidence 锚；不足 3 例进候选区或 watch。
- **负清单例外**：防误标类（WL-04 停用泛称、WL-10 的 decoy）允许**单例实证**入库——一次真实误标即足够，因为其作用是拦截而非召回。
- **外部借源例外**：M3 注释性知识（品级、纪年）允许以 watch/narrative 先验存在，但**永不作为召回依据**，直到语料锚定。
- **专有名词不放宽**：专名恰是误标重灾区，不设"出现 1 次即可入库"的例外（v2 该项作废）；罕见专名走 M1 种子（watch/review 起步）通道，同样受 3+ 案例晋升约束。
- **去重键**：`(surface, canonical, disambig, book_scope)` 四元组表内唯一；表间重复见 §5.5。

### 5.5 一词多表的主表归属与引用制

**主表判定顺序**：① 实体码归属（词的 01g 类别决定主表）；② 同类别多表时按首建表优先；③ 分类树叶子表**永远**是引用方，不做主表。

- 示例（边界案例一）："总镖头"实体码=`;` 职衔 → 主表 WL-02 职衔表（负责 canonical/evidence/tier 维护）；WL-16 职衔分类树叶子表只存 `{ref:"WL-02", key:"总镖头"}`，不复制词条。
- 引用方消费主表数据时展示主表 tier/conf；引用本身不可携带覆盖字段（防止双主表漂移，§九 W04）。
- 两表争夺主表归属时，提交 `_registry.json` 仲裁记录，按判定顺序裁定并留痕。

**理由**：双主表是消歧与搜索错乱的根源；引用制让"叶子清单=词表"（#8 契约）与"一词一主表"两个需求同时成立。

## 六、验证五分类武侠化（Q5）

### 6.1 五分类重定义（白话语料）

| 分类 | 武侠化定义 | 判定要点 | 示例 | 联动 conf |
|---|---|---|---|---|
| tagged | 该词条在 tagged.md 中已有 01g 体系直接标注（如 `〖@练霓裳〗`；别名形"白发魔女"由 WL-01 回链 canonical） | 有标注符号锚 | `〖@练霓裳〗` 已标，surface=白发魔女 入别名表 | strong |
| verbatim | 规范化后在纯文本原样出现 | 逐字命中（含回目——回目也是原文；**白话引语原样出现也算**） | "练霓裳"直书；回末套语全串命中 | strong |
| partial | 变体命中：绰号截称/加缀变体、模板部分命中后补全、省略式 | 经归并规则可还原到完整词形 | "魔女"指练霓裳；"欲知后事"截断式；`人称玉罗刹` 模板填充 | ok |
| narrative | **非正文原文的概括（语料外来源）**：考订表综述、研究文献归纳、集合概念（单点正文无锚） | 语料外来源 | "天山七剑"作为集合称谓的考订表述 | weak |
| unverified | 纯文本找不到且无标注 | —— | —— | **禁入**：修正或删除后方可入库（02h 铁律） |

**与 02h 的关键差异**：文言版的 narrative 指"原文栏是括号叙事（后人概括）"；武侠版把它推广为"一切语料外来源"（考订/研究/集合概念），因为白话章回体没有三家注式的括号注，但考订性叙述同样不可锚定。**"人称玉罗刹"中的"玉罗刹"是语料内可证文本**（partial 级），不是 narrative——把语料内文本归入语料外档会把真实证据错降为 conf=weak（v2 该误定义作废）。

## 七、工作流程

### 7.1 新建一张词表

1. 在 §二 总表登记行（实体码/服务页面/消费方/来源/规模/优先级/构建方式/负责人）——先登记后建数据。
2. 定主表归属（§5.5 判定顺序），若与他表重叠写出引用方案。
3. 建 `<wl>_source.md`：meta 头（表码/版本/负责人）+ 正式条目区 + 候选区 + 归档节。
4. 在 meta.extensions 登记表私有扩展字段；共享池已有字段直接用。
5. 按 §5.1 方式启动构建（M1 直写 / M2 进候选区 / M3 先做 §5.3 许可登记）。
6. 首次派生 + 对账（§4.2 步骤 2-4），进 _registry.json。

### 7.2 新增词条（agent 操作序）

1. 定位主表；查重（四元组键，§5.4）。
2. 填骨架 8 字段；模板条目补 surface_kind；同名补 disambig/book_scope。
3. evidence 锚定（book:loc+kind）；锚不了 → 按 §6.2 判断可否先验 watch。
4. conf 按 §6.3 判定；初始 tier 按 §3.3 派生，**禁止跳级**（§九 W12），**禁止 tier↔conf 互推**（W13）。
5. 过 §5.4 门槛；不过 → 候选区/watch。
6. version=1；跑派生；若影响消费方（新 auto 条目进兜底层）→ 按 §4.4 声明版本。

### 7.3 修订与三档流转

1. 修订只改源表；version+1；重大语义变化（canonical 变更、消歧拆分）须在 notes 留轨迹。
2. 晋升/降级按 §4.3 表执行，流转记录写源表条目 notes（`tier: watch→review@2026-11-03, 依据: 3 案例命中`）。
3. 已核准条目修订后回待审（status 不保留已核准——§3.3）。

### 7.4 版本发布与回滚

1. 发布 = 派生 + 对账 + version 递增 + _registry 更新（§4.2）。
2. 回滚 = 源表 git revert + 重跑派生；派生无状态，不单独回滚 JSON。
3. MAJOR 升版须同步本文档 §3.7 字典与受影响消费方，并在 _registry 留变更记录。

## 十一、FAQ

**Q1：词表是数据不是代码，为什么还要一份"规划文档"？**
因为数据也需要合同。字段、枚举、版本、双轨规则就是词表这种数据的"接口契约"；没有它，五种既有 schema 会继续各长各的，收编成本随表数线性上涨。

**Q2：tier 和 conf 为什么并存，一个不够吗？**
不够。conf 是证据有多硬（"一羽千钧"只有窗口共现），tier 是运营上允许做什么（能否自动补标）。证据弱的词形有时也必须进生产（如负清单 decoy），两者必须解耦——所以"conf 从 tier 派生"或"tier 从 conf 派生"的单轴方案都不成立。

**Q3：status=auto 与 tier=auto 撞名，怎么区分？**
status=auto 指"机器核定通过"（生命周期起点），tier=auto 指"可用于自动补标"（运营档位）。机核通过（status=auto）还须过计数验证/剥标还原才配 tier=auto；04f 既有数据两者同值正是机核通过的结果。

**Q4：conf=weak 永远不发布吗？搜索联想也不给用？**
生产标注管线永不发布（招式表图例继承）。搜索联想属低风险展示场景，是否开例外由附录 B-3 拍板；拍板前一律不给。

**Q5：refs 明明够用，为什么并入 evidence？**
因为多书宇宙必须带 book，且 conf 判定依赖证据类型（kind）。01g 的 refs 结构升级为 evidence 后信息无损、可逆，而招式/动词两表的 evidence 从此同构。升级后不保留 refs 旧列——双写必漂移（W14）。

**Q6："总镖头"到底归职衔表还是分类树叶子表？**
归 WL-02 职衔表（实体码判定）；分类树职衔轨叶子只存引用。叶子表永不复制词条（§5.5）。

**Q7：绰号-本名映射表与 01g 别名四列是什么关系？**
同一张表。01g 四列就是 WL-01 的 schema 前身，迁移按 §3.6 变体一执行；今后表字、道号等别名子类也进这张表，用 type 区分。

**Q8：外部职官表和语料扫描结果冲突听谁的？**
听语料的。surface 与 canonical 以语料锚定为准，外部表只作 notes 注释；分歧写进 notes 供考订裁定（§5.2 双源裁决）。

**Q9：模板语法 `*` 会不会把字面的星号匹配错？**
武侠正文几乎不出现星号；且模板条目必须 surface_kind=template，派生与 lint 按类型分别处理，字面匹配只对 literal 生效。

**Q10：停用泛称表也算词表吗？方向是不是反的？**
是词表，方向确实是反的——它是负清单（signal_role=decoy）。统一 schema 让正负清单同构管理：同样的字段、同样的门槛（单例实证例外）、同样的版本协议，lint 消费时按 signal_role 区向即可。

**Q11：词表版本怎么升？旧批次语料要重标吗？**
条目增删改升 MINOR，字段/枚举变更升 MAJOR。旧批次语料不强制重标，meta 里留着当时版本；lint 只 WARN 不阻断（§4.4-P3）。

**Q12：gazetteer 为什么只做接口对齐不收编？**
650 条地名数据归 #10 专责处理（其消歧与图层体系自成一体，#10 已定稿）；本体系只锁定 conf/status 的落位与版本协议（WL-20 接口注记），避免双头维护。#10 的 conf 枚举已对齐本表 §3.7 字典（strong/ok/weak）。

**Q13：扩展字段为什么扁平放顶层、snake_case，而不是 ext 包裹加小驼峰？**
既有已上线数据说了算：moves-v1/verbs-v1 的实测字段（parent_art/sect/used_by/complements…）全是顶层 snake_case。ext 包裹+小驼峰会让 222 条已上线数据每个字段都改形态，违背无损迁移的最短路径；且"ext 推荐或顶层兼容"两可制必然漂移。故定版：扁平+snake_case+登记制。

**Q14：gazetteer 的 status/verified 与词表的 status/verify 字段名相近，是一回事吗？**
不是。词表 status=生命周期三档（auto/待审/已核准）、verify=验证五分类（条目级证据档位）；gazetteer 的 status 是地名库四档（多一个"已弃用"）、verified 是人工核验布尔、无 verify 五分类。两库各按其定稿文档执行，接口对齐只锁 conf 枚举与版本协议（WL-20 接口注记）。
